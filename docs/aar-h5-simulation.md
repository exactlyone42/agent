# AAR：H5 測試用「模擬」代替真實情境，留下哪些缺口

日期 2026-11-01。範圍：P01 子任務 H5（兩個程序搶同一任務、崩潰於工具前後的恢復）。性質：事後檢討，不追究人。

## 1. 原本要證明什麼

使用者開兩個終端，各跑一個 CLI 程序。要證明兩件事：

1. 兩個程序同時想執行同一個已批准的工具動作，只有一個會真的執行。
2. 程序在動作前或動作後死掉，重開後不會把已經做過的動作再做一次；不知道有沒有做成的動作，要標成「結果未明」，不能盲目重送。

## 2. 實際做了什麼（測試檔 `crates/agent/tests/contention.rs`）

| 要證明的事         | 實際測的方式                                                   | 和真實情境的差別                                                                                                                         |
| ------------------ | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 兩個程序搶同一批准 | 同一個程序開兩個執行緒，各開一條資料庫連線，同時搶。重複 10 輪 | 真實是兩個獨立程序。資料庫鎖是以連線為單位，所以搶輸的判斷有被測到；但沒測過兩個程序各自的啟動、檔案鎖與等待逾時                         |
| 動作後崩潰         | 把連線關掉，再開一條新連線                                     | 真實崩潰是程序被殺掉（例如 `kill -9`）。關連線是乾淨結束，資料庫會整理好暫存檔；被殺掉時寫到一半的資料要靠資料庫重開時修復，這條路徑沒測 |
| 動作前崩潰         | 同上                                                           | 同上                                                                                                                                     |

## 3. 為什麼這樣做（前因）

- 現有資料存取介面（`TaskStore`）可以在測試裡直接呼叫，成本低。
- 真雙程序要啟動 CLI 執行檔、讓它停在指定位置再殺掉，需要同步機制。專案已有 `crates/cli/tests/cli/sync_pipes.rs` 這類同步管線，可以沿用，但我當下沒有先評估，選了較便宜的做法，並且在回報中寫了限制。
- 判斷依據：想驗的「只派發一次」邏輯在一條資料庫交易內完成，執行緒與程序對它的影響相同。這是推論，不是實測。

## 4. 「卡在 running」是怎麼來的（因果鏈）

1. 任務一開始，紀錄寫成 `running`（`store.rs` 的 `create_task`）。
2. 任務結束時，只有 `finish()` 會把狀態改成成功、失敗或結果未明，同時把「已派發但沒回執」的動作標成結果未明（`close_intents`）。
3. 程序在步驟 1 和 2 之間被殺掉，`finish()` 沒人呼叫。
4. 專案目前沒有「重開後接手並收尾」的程式。我搜尋 `crates` 目錄，沒有找到 resume、recover 或租約相關程式。
5. 結果：任務紀錄永遠是 `running`，該動作永遠是 `dispatched`。

這個狀態是安全的一面：動作已經用掉批准次數，重開後再搶只會得到「拒絕」，不會重送。不好的一面：沒人把它標成「結果未明」，使用者看到的是永遠執行中。

## 5. 我的測試比現實樂觀的地方

`crash_after_dispatch_...` 測試在重開後，手動呼叫了 `finish()`，才看到「結果未明」。現實中沒有人會呼叫它。所以這個測試證明的是「只要有人收尾，結果就是對的」，不是「崩潰後系統會自己變對」。後者要等 P04 的 `resume`。

## 6. 做對與做錯

- 做對：用破壞程式的方式確認測試有效。把「批准用掉後次數歸零」改壞，3 個測試有 2 個失敗。
- 做錯：測試名稱 `crash_after_dispatch_is_never_dispatched_again_and_stays_unknown` 讀起來像崩潰恢復已被證明，容易讓人高估。
- 做錯：進度表當時寫的「DONE」過於樂觀。H5 的驗收欄原文要求「雙程序測試；崩潰注入」，實際沒有達到。
