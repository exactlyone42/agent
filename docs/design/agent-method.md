# 整個 Agent 如何工作：方法、證據與驗收

研究日期：2026-10-26。這份文件是全案的運作契約（程式與人都要照做的明確約定）與研究結論，不是實作完成報告。主計畫的交付順序是先做命令列工具 CLI，再做桌面版 ADE（讓人派工、批准與驗收的工作台，放在另一個 repo agent-ade，不做完整 IDE）；知識細節見 [knowledge-plan.md](knowledge-plan.md)。先前的研究只涵蓋局部能力，本文件補上整體。產品與發布範圍以唯一的 [主計畫](../../PLAN.md) 為準；本文件只定義執行契約，發現衝突就同步修正，不另立主計畫。

2026-11-16 起，核心的名稱、由多項「能力」組成的結構，以及排程算法（多件事等著做時決定先做哪件），以 [mortal agent](mortal-agent.md) 為準；本文件的任務欄位與驗收契約仍有效。

## 先定方向，不把功能名稱當成答案

採一個可替換的執行核心（Harness，負責驅動「模型決定、工具執行、結果回饋」迴圈的程式），把模型決策、工具執行、任務紀錄及獨立驗收分開。第一版只有一個 Agent（能自己決定下一步並呼叫工具的 AI 程式）；步驟明確的事用程式做，步驟未知時才讓模型選下一個動作。模型不能批准自己、不能改完成條件、不能忽略取消，也不能把自己說的「做完了」存成成功。Gateway（另一個 repo、統一轉接各家模型的服務）只供應模型 API，不接管本機授權。

證據分三種：**規範／官方實作**說明介面與現有做法；**論文實驗**只支持特定資料、模型與任務的結果；**本案決策**須以實際試接（真的把元件接起來跑一遍）驗收。以下「常見工程做法」指能在官方產品或框架找到，不代表已量測市場占有率；「研究支持」不代表全領域保證有效。預印本（尚未經同行審查的論文）不會被說成已通過審查。

先認識幾個詞，表格與後文會用到：

- 副作用：動作對外部造成的改變，例如寫檔、發請求。
- schema：事先規定好的欄位名稱與型別。
- 冪等：同一請求送一次或多次，結果相同。
- 世代：同一任務每次重新接手執行就換一個新編號；舊編號送回的結果不能蓋掉新編號的結果。
- 領用授權：用掉一次批准，剩餘可用次數（uses_remaining）減一。
- 符號連結：指向另一個路徑的捷徑檔。
- RAG：先搜出相關原文，再讓模型依原文回答；本案分三塊，見後文。
- MCP：讓模型接上外部工具的公開協定；rmcp 是它的 Rust 套件。
- Docling、LlamaIndex：文件解析工具與資料處理框架，見 knowledge-plan.md。
- Codex、agent-harness：兩個候選執行核心；前者是 OpenAI 的程式開發 Agent，後者是本案自寫的。
- P01–P10：主計畫的階段代號，例如 P01 核心迴圈、P05 知識檢索、P06 記憶。

## 審查後補齊：最小欄位與執行規格

以下是待實作的 schema 規格，不是已存在的資料表。識別碼用 UUID 字串（隨機產生的唯一編號），時間用 UTC，金額用固定精度（小數位數固定）；所有紀錄帶 schema_version（格式版本號）。程式只接受已知的版本與列舉值（事先列好的選項）。遇到未知欄位，依協定版本規則拒絕或明確忽略，不靠模型猜。

| 紀錄         | 最小欄位                                                                                                                 | 唯一寫入責任                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| TaskSpec     | task_id、spec_revision、original_request_ref、workspace_id、goal、criteria[]、policy_revision、budget、state、generation | 平台核心；模型只能提出候選，使用者修正產生新版                       |
| Criterion    | criterion_id、type（file/api/gui/semantic）、expected_ref、verifier_id、required、reviewer_role                          | 固定任務模板或使用者原需求決定，獨立驗收者鎖定；執行模型無權自行降低 |
| ToolIntent   | call_id、task_id、step_id、generation、tool_version、args_ref、args_hash、approval_id、idempotency_key、status           | 核心派發端；意圖與授權領用同一交易                                   |
| Approval     | approval_id、principal、scope、tool_version、args_hash、policy_revision、expires_at、uses_remaining、revoked_at          | 授權服務；使用者已授權範圍可由政策判定，不由模型批准                 |
| Receipt      | call_id、attempt_id、status、external_ref、artifact_refs、started_at、finished_at、error_code                            | 工具執行端提交，核心驗來源及世代後保存；模型文字不當回執             |
| Event        | event_id、task_id、seq、generation、type、payload_ref、created_at                                                        | 核心追加；task_id＋seq 唯一，重播不派工具                            |
| Evidence     | criterion_id、verifier_version、artifact_hashes、observed_state、verdict、checked_at                                     | 獨立驗證器；產物與規則改變就失效                                     |
| Memory       | memory_id、principal、workspace_scope、content_ref、source_refs、consent_id、status、valid_from、expires_at、revision    | 記憶服務，模型僅送 candidate；有效性與同意由程式／人工核定           |
| SourceAccess | source_id、principal、scope、policy_revision、source_version、status、checked_at                                         | 知識服務保存主機可讀檢查結果；不是自行授權。來源取回時重驗           |

任務規格與 Evidence 保存於平台 SQLite（單一檔案的本機資料庫）；大內容放使用者專屬的受限檔案。Memory（經使用者同意保存的長期記憶）初版的候選、有效內容與來源對應，也用平台 SQLite（內容設大小上限，或只存檔案引用），先按使用者、工作區、期限篩選，再查內容；沒有需要時，不增加向量記憶系統。與知識庫來源連動，靠來源版本及撤回事件；讀取端要再查一次是否仍有效，因為兩個資料庫不能當成同一筆交易，本案也不聲稱做得到。這修訂了此前 P06（記憶階段）保存位置未定的狀況。

工具回應裡的「請永遠記住」不算使用者同意，記憶不接受。使用者明確表示的偏好，可依其範圍保存；AI 寫的摘要與失敗經驗先當候選，附可讀回的證據。使用者撤回後，立刻停止把它放進給模型的輸入，由它衍生的快取同步失效；實際刪除與備份的保存期限，按使用者授權處理，不擅自刪資料。

### 合法狀態與完成條件

| 目前狀態                     | 可前往                                                                 | 必要條件                                             |
| ---------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------- |
| queued                       | running、cancel_requested                                              | 核心取得工作區鎖與執行世代；取消優先核對             |
| running                      | waiting_approval、verifying、failed、cancel_requested、outcome_unknown | 真實事件觸發；不得因模型文字直接成功                 |
| waiting_approval             | running、failed、cancel_requested                                      | 批准有效且對應當前規格；拒絕不轉為批准               |
| verifying                    | succeeded、running、needs_review、failed、cancel_requested             | 全部必要條件通過才成功；修正尚有預算才回 running     |
| cancel_requested             | cancelled、outcome_unknown                                             | 可控程序確實停止且外部結果已核對，否則結果未明       |
| outcome_unknown              | verifying、cancelled、failed                                           | 查得真實回執後由恢復協調者決定；禁止直接重新派副作用 |
| needs_review                 | verifying、cancel_requested                                            | 等待具名驗收者或補足可執行判準，不再自動修正         |
| succeeded、failed、cancelled | 不直接重開                                                             | 接續建立新 run／generation，先核對舊程序與已生效動作 |

沒有標準答案的研究、設計與寫作，仍有程式能檢查的項目（必答問題、來源、產物、格式）；內容是否正確、是否達成目的，由獨立的人工規準驗收。判準不足時可交候選產物，但狀態是 needs_review（待人審），不冒稱 succeeded。AI 評審僅提供建議，不能修改完成條件 criteria；人類驗收也留版本與理由。

### 模型與 CLI 協定

本輪只讀程式碼、沒有執行，核對 Gateway 的 `src/routes.rs:34–39`，確實登記了 `/v1/chat/completions`、`/v1/responses`、`/v1/messages` 三個路徑；路由存在，不證明目前每個模型或 Codex 都相容。P01 的能力表（記錄各模型實際支援什麼）必含這些欄位：wire_protocol（通訊格式）、model_id、streaming（串流輸出）、tool_schema、parallel_calls（同時呼叫多個工具）、image_input、context_limit（上下文長度上限）、cancellation、usage_reporting。每個值都帶實測版本，未知就不啟用該能力。Codex 路線先測 Responses（OpenAI 的 API 格式）從頭到尾可用，Rig 路線依已選 provider（模型供應商）的原生協定；未通過就不做不明的轉譯補丁。

串流（模型邊產生邊回傳）時，工具參數收齊並通過 schema 檢查後才執行；用 call_id 對應回覆，不從文字猜工具名。串流中斷後重連，可以重播事件，但不得再次領用授權。核心候選必須同時做到四件事，任一件不過就淘汰：所有工具（含內建 Shell，即命令列執行器）都能被限制；最後派發的那一刻能核對授權與取消；外部能停止執行；結果能獨立讀回。

CLI 契約保留 run（執行）、resume（接續）、status（查狀態）、doctor（自我檢查），補上 cancel、approve/deny（批准／拒絕）、events（讀事件）。非互動批准必帶 approval_id 與預期的 spec_revision，讓批准只對那一版規格有效。輸入走 stdin 或受限檔，不在命令列帶秘密。事件用逐行 JSON，欄位沿用 Event；stdout 只放結構化結果，診斷放 stderr。events 接 after_seq，只回該序號之後的事件。桌面版隨應用啟停子程序，使用同一協定；schema 不相容就拒絕，不解析終端文字。斷線後先查 status 並補讀事件，不能把重新連線當成 resume。未知命令與無效狀態都不能觸發工具。

### 隔離與平台的具體選擇

Windows／macOS／Linux 均須滿足同一隔離契約。Linux x64 試接選 **bubblewrap（Linux 的輕量沙箱工具）隔離一次性 Shell**：基本執行環境唯讀、只有明列的工作區可寫、暫存獨立、預設無網路，不掛 SSH agent（代管 SSH 金鑰的程式）或完整的主機家目錄；[官方](https://github.com/containers/bubblewrap)明確指出，隔離強度取決於呼叫時給的參數，不是裝了就安全。缺少 user namespace（讓程式在隔離環境內有獨立使用者身分的 Linux 功能）或必要限制時，拒絕敏感工具，不靜默退回沒有隔離的 Shell。模型的網路由核心走 Gateway；Shell 需要網路則另走已批准的能力。

常駐的解析與索引服務仍放在容器（隔離的執行環境）。優先試：不用 root（最高權限）執行並明確對應 UID（使用者編號）、來源唯讀掛載、parser（文件解析器）無網路、資料庫只供內部服務。[Docker rootless](https://docs.docker.com/engine/security/rootless/)（不用 root 跑 Docker 的模式）有主機端先決條件，由安裝器檢查，不自動調整使用者的系統服務。操作主機桌面畫面（GUI），只由使用者啟動的前景 CLI 或桌面子程序呼叫既有驅動；不把主機的桌面 socket（程式間通訊的連接點）整個開給背景容器。Linux 的隔離試接先用 X11（Linux 傳統的圖形系統）。Windows、macOS 的原生桌面與 Linux 受支援的桌面會話，必須各自完成 P07（電腦操作階段），都不得降為後續選項。

憑證優先存在作業系統的憑證保管庫（keyring）；沒有可用的保管庫時，才用只有使用者本人可讀寫（權限 0600）的設定檔。憑證在啟動時不得寫入一般日誌，也不得傳給 Shell 或 parser。檢查平台能力的 probe（探測程式）必含秘密 canary：先放入一個假秘密，再確認它沒有漏到日誌或子程序。這些均為選型提案，未在此輪安裝或驗證。

P05a 的最小試接可用人工合成的工作區資料，但產品本身仍是在使用者授權下，逐步發現整台電腦的資料；不得把測試的起點縮減成最終需求。測試依序是：單一範圍、跨範圍且權限不同、整機大量清單，最後驗證常駐更新。2 CPU／4 GiB 先約束基準的解析與索引，不保證 OCR（圖片轉文字）或大型語言模型能同時運行；放不下就排程延後或重新選型，不放寬限制來冒充合格。

### 樣本與判定補充

30 題×5 次只作 P01/P02 的候選比較篩選，不是產品發布認證。固定隨機種子與版本，並列每題五次的結果。同一題的五次結果彼此相關，不能當成 150 個獨立樣本，所以按任務家族做成對重抽樣（反覆抽樣估計差異範圍）區間。安全案例以是否出現未授權副作用判定，任何一次出現就拒收該版本，但零次不表示真實風險為零。成效選型需目標指標改善且成本不超標；區間重疊或某個分組退步，就標示證據不足。發布前要擴充到全部宣告的任務類型，並用真 Client（真實的使用端程式）跑原有的全套驗收，不用這 30 題代替。

### 複審後明確化的三個邊界

**Codex 事件保存**：Codex 自己已經記錄它的執行狀態。平台 Event 只是為了顯示、政策與驗收而從中投影出來的副本，不是 Codex 執行狀態的第二個寫入者。為此增加 origin、source_session_id、source_event_id 或 source_offset 欄位，用來源識別去重；「讀到哪裡」的來源進度與投影放在同一個 SQLite 交易提交，兩者才不會對不上。Codex 核心事件透過它支援的介面同步進來，平台不得直接改寫它的執行狀態。平台的取消與批准只是命令請求，收到核心回執後才形成對應事實。若固定版本沒有可靠的事件識別或恢復途徑，就以 P01 同題驗證是否能安全重建；做不到就淘汰。Rig 路線則由平台本身產生執行事件。Event 表中的「核心追加」，應按此區分來源事件與投影事件的寫入者。

**記憶升格**：使用者明示要保存的偏好，在四項都成立時，由程式轉為有效，不需要模型再猜同意：原訊息可定位、scope（適用範圍）明確、有效同意存在、沒有互斥的新版。從任務學到的經驗，必須附獨立驗證成功的 Evidence，且適用條件可寫成明確範圍；無法由規則核對的經驗，須具名人工確認，否則留在 candidate（候選）。來源撤回、驗證版本變更或新偏好衝突時，先使它失效。AI 生成的摘要，不能只靠自己提供的引用就升格。

**來源權限映射**：source_id（來源編號）與內容雜湊是分開的。每個 source_id 保存授權根目錄、主機使用者的 UID/GID（使用者與群組編號）、相對路徑與檔案識別、政策世代，以及有效的來源版本。容器依該使用者的明確對應執行，只掛載授權根目錄；容器內 root 讀得到，不能當成主機上有權限。身份或 ACL（存取控制清單，記載誰可讀寫該檔）無法可靠對應的來源，標為不支援，不能因此改成全部允許。內容去重可以共享計算，但每次引用都要經過各來源自己的授權；摘要若跨來源，使用者須同時有權讀全部依據。SourceAccess 是可撤銷的核對結果，不是新的授權來源。檢索、補讀、送模型之前，都要核對當前政策，並以同一身分實際開啟原文、檢查版本。測試要涵蓋：兩個根目錄內容相同但權限不同、撤銷群組存取、符號連結換目標、檢查之後檔案被替換。任何狀態未知，都拒絕把片段送出。這些為試接契約，並未宣稱消除了所有競爭空窗（檢查完、使用前狀態被改掉的空隙）。

## 工具、授權與隔離：真正阻擋動作的位置

[S5 MCP tools 規範 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)定義工具與 schema，不自動替應用程式提供權限隔離。內建工具、MCP、Shell、瀏覽器及 Computer Use（讓模型操作電腦畫面）必須共用同一套授權決策；只把 MCP 設成安全，Shell 仍可能繞過它。

授權紀錄綁定這些條件：使用者／任務、工具版本、正規化（統一寫法）後的參數摘要、路徑或服務範圍、期限及可使用次數。已有持續授權就照用，不能每一步都再問；超出範圍才請使用者決定。LLM（大型語言模型）只提出請求，程式在最後派發點核對。寫檔時核對實際開啟的目標，不能只比字串路徑；Shell 的任意子程序與網路權限，要由實際的隔離環境限制，不只靠命令黑名單。

工具回應是資料，不可冒充上層指示；外部內容同樣不可授權外送、寫檔或安裝。要設定來源允許清單、只讀掛載、輸出上限、程序及網路限制；憑證由工具端取得，模型不接觸原始秘密。已批准不代表對該工具所有未來參數永久放行。

## 上下文、記憶與知識：三種不同的保存

- **任務進度**：確實記下實際發生的動作、授權與回執（工具執行後回傳的憑證）；恢復時不能只靠模型寫的摘要。
- **短期上下文**：目前模型看得到的目標、最近觀察、必要原文與事件摘要；可壓縮，但原始證據在受限產物保存，普通日誌不含全文。比賽版不壓縮：先把任務拆成能獨立完成的工作項，一項一段新對話，靠進度紀錄接續並從外部狀態重建（使用者 2026-11-19 定，見 [mortal-agent.md](mortal-agent.md) 的 P14；效果未實測，見 O12）。
- **長期記憶**：經同意保存的使用者偏好與已驗經驗，附來源、時間、範圍及撤回方式。不是自動把所有聊天當成永久事實。

## 三塊 RAG 放在整個 Agent 的哪裡

向量化 RAG（把文字轉成數字向量，依語意相近度搜尋）提供證據搜尋；Agentic RAG 是同一 Harness 裡的主動查證任務，由 Agent 決定下一步查什麼；知識庫保存版本化來源、可核對知識與解答。這不是三個自行批准、自行循環的 Agent。詳細格式、全機漸進建庫、語意切片與虛擬問題（模型替原文片段事先想好的提問）見 [knowledge-plan.md](knowledge-plan.md)。

本案初始搜尋基準：結構切片（依標題、段落等結構把文件切小段）、原文向量、關鍵字搜尋、去重與原文引用。優先比較重新排序（用另一個模型把搜到的候選重排）與補回上下文（把鄰近段落補回來）；再分別加語意切片、問題多向量、背景說明與多問法。E5（向量模型）候選依其正規化規格使用內積；向量距離用 cosine、內積或 L2，依模型而定，與 HNSW／IVFFlat 這類近似索引（用少量誤差換搜尋速度）是兩回事，不能混為一談。索引加速要對照相同權限條件下的精確搜尋，測近似找回率、更新積壓與熱門篩選後回傳不足。

## 資料保存、重試、取消與恢復

SQLite 保存平台任務／授權／事件；知識內容與向量留 PostgreSQL（另一種資料庫，向量搜尋用其 pgvector 擴充）；大型附件與受限回執留檔案，資料庫記路徑與雜湊。採 Codex 時，核心進度以其介面為準，SQLite 只存平台映射與政策。任務、授權及事件需一起提交的資料，放在同一個資料庫的短交易裡；跨資料庫不能宣稱原子完成（要嘛全成功、要嘛全沒發生）。

[S11 LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)區分快照與跨任務記憶；[checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)說明保存機制。這支持保存與恢復要分層，不證明外部副作用恰好執行一次。採 SQLite 的 WAL（預寫日誌，先寫日誌再改資料檔）、FULL 同步（每次提交都等資料真正寫到磁碟）、備份及限制，見 [S12 官方](https://sqlite.org/wal.html)。

2026-10-27 實作前補查：SQLite 官方記錄，多連線同時寫入或整理日誌（checkpoint）時，可能觸發 WAL-reset 缺陷而損壞資料；3.51.3 起已修正，另有指定舊版的修補。新實作固定使用至少 3.51.3 的已修補版本，啟動及驗收時讀回實際的 SQLite 版本，不只看 Rust 套件版本（套件版本不等於它內附的 SQLite 版本）；WAL 僅用本機檔案系統，不把網路磁碟當成支援的部署。來源：[官方缺陷與修補說明](https://www.sqlite.org/wal.html#the_wal_reset_bug)。Rust 候選採 rusqlite（Rust 的 SQLite 套件）的明確交易介面，失敗預設回滾（撤銷該次寫入）；尚未加入依賴，也未通過持久任務驗收。

狀態與轉換見前面「合法狀態與完成條件」表。補充規則：只有獨立驗證通過才能進 succeeded；取消請求不等於 cancelled；結果未明（outcome_unknown）不可盲目重送。排程器先檢查已有任務與執行者，不能因心跳（執行者定期回報「還活著」的訊號）逾時，就同時派第二份。

有副作用的工具，先在短交易保存意圖並領用授權，之後才派發並保存回執。資料庫寫入與作業系統啟動程序之間仍有空窗，所以必須由單一執行者序列化派發與取消，重啟時核對程序身分與外部回執。每次嘗試有獨立識別及世代；舊世代的回報不可覆寫新世代，但世代欄位本身阻止不了外部寫入。

取消依序做三件事：先停止派發，再停止本機可控的程序樹（主程序與它啟動的所有子程序），最後查證。遠端服務已開始的行為，未必撤得回。無法確認時，保留 outcome_unknown。補償動作（用另一個動作抵銷已發生的結果）不是回滾；若它會刪除資料或產生新副作用，仍須相應授權。「10 秒沒有寫入」僅是案例觀察，不能當取消的保證。

模型請求與工具請求分開重試。遇到 429（HTTP 的「請求太頻繁」狀態碼）時，尊重 Retry-After（回應標頭中指定的等待時間）；超時或串流中斷時，先查現況，沒有回執不等於沒執行。只讀請求可有界重試（設次數上限）；具副作用的請求必須有冪等識別（讓重送不會重複執行的編號）或查證途徑。模型切換只發生在清楚的步驟邊界，不重送已派出的工具；保留版本變更事件，禁止用另一個模型掩蓋待查證的狀態。

## 電腦操作與使用者介面

優先用穩定的 API／檔案工具；必須操作畫面時，採既有驅動（控制視窗與輸入的現成程式），沿用 observe（觀察）／action（動作）／verify（核對）／cancel（取消）契約。驅動是否支援 Windows、macOS、Linux 各自的顯示環境、無障礙樹（作業系統提供的畫面元件結構）、截圖及輸入，須逐項試接；候選名稱不代表已支援。每個操作綁當次觀察與視窗；焦點或縮放改變就先重新觀察。鎖屏、休眠與使用者搶回輸入時，停止派發並記錄狀態。

CLI 先支援任務、授權、取消、接續及結果；ADE（另一個 repo agent-ade）經本 repo 的事件契約，取得同一份資料與事件。介面重連時依事件序號補讀；重送批准時帶識別，避免同一批准被領用兩次。關閉視窗時，前景任務依產品契約停止，或交給容器裡的 worker（背景工作程序）接手，不默默變成常駐。完整 IDE 不做；把 Orca（既有的桌面 Agent 工作台產品）改造成本產品，只保留作比較，不在本輪改選。六家產品比較留在主計畫；競品有桌面版，不代表我們必須重造編輯器。

## 安裝、觀測、升級與效能也是方法的一部分

原生 CLI 啟動時不依賴 RAG 服務；完整知識版在本機容器提供依賴。安裝器先檢查平台、容器、磁碟、來源範圍、模型大小與授權，缺項明示，不默默花錢或上傳。要鎖定的版本包括：可執行檔版本、依賴的 lockfile（記錄各依賴確切版本的檔案）、容器 digest（容器映像的內容雜湊）、模型 revision（模型版本編號）及授權。升級須驗 schema 遷移、備份還原及版本不相容時會拒絕。下載校驗與簽章信任來源分開；只看同一網站上的 SHA 雜湊值，不能稱供應鏈安全，因為檔案被換掉時，同站的雜湊值也可能一起被換。

每個任務記 task／run／step／tool call 的識別、時間、狀態、重試、模型用量與驗收位置；普通日誌不記秘密與完整資料。原始證據放受限產物，有保存與撤回規則；錯誤不能吞。保存範圍也納入磁碟預算，達限就暫停新工作，不自動刪使用者資料。常駐程序遵守容器及 loopback（只接受本機連線）限制；單次 CLI 子程序不冒稱常駐服務。
