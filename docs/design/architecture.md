## 每個部件開發前必須具備的契約

每個部件都要先定義下列項目，合稱它的契約（和其他部件約定好的輸入、輸出與行為）：目的與非本部件責任（哪些事不歸它管）、輸入輸出與版本、身分與權限、資料擁有者、錯誤種類、逾時與取消、可否重試及副作用（除了回傳結果，還對外改動了什麼，例如寫檔）、資源預算、事件與診斷、升級遷移／回退（升級時搬移資料，出問題時退回舊版）、替換測試、程式／AI／真人驗收。缺項在開工前補清楚；不得寫完才發現另一個部件也在改同一份狀態。

所謂彈性，是契約明確，而且換掉某個部件後有測試證明仍能運作；只在程式裡宣告 interface（描述「能做什麼」的介面）名稱，不算彈性。對外部依賴，優先經一層很薄的轉接程式接入。只有需要隔離或常駐時才拆成獨立程序，常駐服務放容器。不要為了表面上模組化，把每個函式都做成微服務（各自獨立部署的小服務）；也不要讓 UI、政策與資料庫被綁死在某一家模型的 SDK（開發套件）上。

## 整體完整性檢查

每張開發卡（一項工作的紀錄）都要標出上表中涉及的部件及其上下游（前後相接的部件），不能只驗證自己寫的函式。至少要有下列六條整合流程，每次都固定程式、模型、設定與資料的版本：

1. 安裝 → 初次設定 → 任務 → 授權 → 工具 → 獨立驗證 → 成果 → 稽核。
2. 同意來源 → 發現 → 解析 → 切片 → 向量／全文 → 主動查證 → 知識發布 → 改檔／撤權 → 舊答案失效。
3. 工具執行前後崩潰 → 核對副作用 → CLI／桌面接續 → 不重複動作；取消覆蓋整條程序與工具鏈。
4. 企業政策變更 → 待授權及進行中任務重新核對 → 知識、快取、工具與模型外送同步服從；兩個資料庫無法保證一起成功或一起失敗（跨庫交易）時，每個使用資料的地方都要再核對一次版本。
5. 升級前備份 → 安裝／資料遷移 → 任務與知識讀回 → 模擬失敗 → 已驗證的還原；已被撤回的舊權限，不可因為還原而復活。
6. 背景建庫（建立知識索引）與前景任務同時執行 → 限額／斷網／磁碟滿 → 可觀測降級（功能縮減但能從紀錄看到）及接手 → 恢復後核對結果；不把服務健康當任務成功。

SQL 效能要靠查詢與容量測試確認，不能因為用了某個資料庫就當作夠快。任務表依工作區、狀態、時間建索引（加速查詢的目錄），事件表依任務、序號建索引，待處理工作也建索引。查詢要分頁、批次要有上限，不做沒有上限的逐筆呼叫。查詢計畫（資料庫決定怎麼執行查詢的步驟）、鎖等待（等別人放開鎖的時間）、WAL 大小及 P95（95% 的請求在這個時間內完成）隨版本記錄。SQLite 的 WAL 仍是同一時間只有一個寫入者；[官方說明](https://www.sqlite.org/isolation.html)不支持把本機資料庫當成跨機器共享的服務。

## 給外部實作者的契約

契約依階段固定（P02 這類代號是 PLAN.md 的階段編號）：P02（可用的 CLI）固定任務（Task）的啟動、查詢、事件、授權與取消；P05（知識檢索）固定知識（Knowledge）的匯入與查詢；P06（記憶）固定記憶（Memory）的寫入、查詢、更新與撤回；P07（電腦操作）固定電腦操作（Computer Use）的能力、觀察、操作、驗證與取消。接法在 HTTP、MCP 與程序介面（啟動程序後透過它的輸入輸出溝通）中，依現成能力選最簡單的一種，不同時為每個模組做三種協定。

每個契約都含：版本、request ID（請求編號）、授權 scope（授權範圍）、deadline（期限）、取消語意（取消後各部件要怎麼動作）、型別化錯誤（有固定種類的錯誤）與結果未知狀態（無法確定成功與否）。外部服務必須自己再驗身分與授權範圍，不能信任任意 Client 傳來的 owner（資料擁有者）。第二個 CLI Client 必須能獨立使用，才算可以交接；只是共用 Rust 內部型別，不算跨語言契約（用別種程式語言也能照著實作的約定）。

流程是：Agent 收到文件後，可呼叫知識檢索；工具得到結果後，回傳給 Harness（執行核心），由 Harness 決定下一步。Gateway 只接模型請求。Computer Use 不掌管整個任務的流程；Evaluation 在旁邊建立測試環境並驗證結果，不是讓產品用的模型替自己評分。

## 三平台完整性

Windows、macOS、Linux 都是必要交付。除了三平台共用的核心，下列項目要各自有平台轉接（針對各作業系統分別寫的銜接程式）：作業系統身分與 ACL、路徑、檔案監看、秘密存放、Shell 隔離、子程序取消、電腦操作、容器，以及安裝與更新。各轉接支援哪些 OS／CPU、安裝包怎麼提供、誰負責驗收，以[主計畫三平台矩陣](../../PLAN.md#三平台是正式範圍不是後續選配)（各作業系統與 CPU 組合的對照表）為準。每個轉接都要通過同一份契約，並在原生實機（真正的該系統機器）上做整合測試。Linux 的 bubblewrap（Linux 專用的程序隔離工具）不能當作 Windows／Mac 的沙箱（隔離環境）；WSL（Windows 內的 Linux 環境）也不能當作 Windows 原生桌面。
