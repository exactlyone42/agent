## 統一檢查入口

2026-10-27 已建立快檢入口。2026-10-29 它從 Python 與 shell 腳本改寫為 Rust 的 xtask，命令是 `cargo xtask gate`。它先依 docs/directory-structure.md，檢查 Git 追蹤的檔案（已納入版本控制的檔案）的目錄結構，也就是檔案放得對不對，項目有：未登記的頂層項目、crate 內項目、雜物目錄、空檔案、執行產物（程式跑出來的輸出檔）、放錯位置的腳本與文件、沒人引用的文件、逐字重複的文件段落、產品原始碼裡的中日韓文字（訊息表除外）。

結構檢查之後，它再實際執行這些檢查：格式檢查；全部 target／features 的 Clippy；生產函式庫／執行檔（正式交付的程式，不含測試）的 unwrap、expect、panic、todo、unimplemented、unreachable、assert 系列（斷言，條件不成立就中止程式）與 mod.rs 禁用檢查；未用依賴檢查；以及 workspace（含多個 crate 的 Cargo 專案）的測試。禁止模式用編譯器規則檢查，另用 1 個合法與 13 個違規樣本，確認規則確實會擋；測試程式仍可使用斷言。未用依賴使用 cargo-machete 0.9.2 檢查。

`all` 已接上快檢、工具版本、秘密掃描、測試覆蓋率與整個 workspace 的變異測試。每輪的原件（原始輸出）各存在 `.runtime/checks/` 下一個獨立的目錄；任何命令失敗，或檢查前後的程式雜湊（內容指紋）不同，都不通過。秘密掃描的範圍是 Git 列出的、現在存在且沒被忽略的檔案；它包含未追蹤檔，排除 Git 忽略的建置產物與本輪原件，所以不能當成整機的秘密掃描。

還沒接入的有：未參與編譯的孤立檔案（寫了卻沒被編譯到的程式檔）、模型設定規則與三平台整合驗收，所以 P01 品質底座尚未完成。Linux 通過不代表 Windows／macOS 已實測；執行環境要先裝好上述工具與 Clippy。

P01 要建立 `cargo xtask gate`（快檢）與 `cargo xtask all`（推送前跑的全套檢查）。命令還沒建好時，不可假裝通過。底層至少執行下列命令：

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo test --workspace --all-features --locked
npm ci
npm run format:check
npm test
```

資料庫測試放在隔離的容器內跑。變異測試、覆蓋率、未使用程式、秘密掃描、檢查規則的自我測試，以及桌面／外部 Client 的驗收，都由 all 納入。cargo-mutants（Rust 的變異測試工具）與覆蓋率的精確參數，P01 依實際的 crate 設定，不能填不存在的套件名。API 或桌面行為有改動，要有對應的整合驗收；只改文件時，不編造 Rust 測試。

## 安裝狀態與版本

本機已查到 Rust 1.98.0、rustfmt、clippy、cargo-mutants、cargo-llvm-cov（算覆蓋率的工具）、Node 22、npm 10。這只代表本機裝了工具，不代表依賴彼此相容，或 Agent 能建置成功。P01 必須記錄實際版本並產生 lockfiles（鎖定依賴版本的檔案）。Rust workspace 與 Cargo.lock 已建立。桌面在另一個 repo agent-ade，本 repo 不建置桌面。

共用 Git policy 程式（提交與推送時檢查分支、訊息的腳本）原樣復用，來源雜湊可核對；不重寫它們，不刪原始來源（上游）的註解，也不改寫它們來規避測試。自寫程式不加註解，必要說明放在文件。規劃期只檢查：Markdown 格式與連結、JSON、共用 policy 測試、敏感檔案與 Git 差異。程式品質門檻要等 P01 真正接入，不能把本文件當成已強制生效。

## CI與發布

CI（每次推送後自動執行檢查的服務）的設定在 P01 寫好，並先在本機做對等驗證（跑和 CI 同樣的檢查）；沒確認免費額度前，不啟動可能計費的 runner（執行 CI 的機器）。沒有部署用的 workflow（CI 流程設定檔）；push 不是部署。第一次在空 repo 建立 develop，不代表發布版本，也不建正式服務。之後合併要依已授權的規則與真實的 CI／驗收狀態，不能用管理員權限繞過分支保護。

完整檢查會暫時修改 Rust 原始碼，來驗證測試抓不抓得到錯誤，所以期間禁止其他執行者編輯或編譯；目前由唯一的工作流程持有專案鎖（防止同時操作的標記）。每輪輸出包含開始與結束時間、退出碼（程式結束時回報成功或失敗的代碼）、工具版本、來源雜湊與平台。`summary.json` 在本機通過，不能代替人工簽收。若程序被強制終止，沒有 summary 就視為未完成，要先核對來源再續跑。秘密檢查本身用合成 token（為測試造的假 token）驗證能偵測與遮蔽；檢查器的成功、失敗及工具不存在，都有測試。

2026-10-27 全套實際跑過一次，得到 80 個變異結果（80 個被故意改壞的版本各自的測試結果）。Windows 上沒執行到的程式路徑，以及等價變異（改了寫法但行為沒變的變異），這兩項都待正式裁決，所以完整門檻未過。覆蓋率的原始報告固定存在 coverage-report.json，執行紀錄另存在 coverage.json；已有覆寫的回歸測試（防止曾出現的錯誤再發生）。秘密掃描只對已核對過的請求快取 UUID（隨機產生的編號）放行，其他憑證仍照常檢查；快照（掃描前複製出來的檔案副本）是空的就拒絕。完整入口會保留 active.json（標記完整檢查正在進行的檔案）直到正常結束；中斷後要先核對程序與來源，不能直接刪掉標記重開。最新的分項證據放在 `.runtime/checks/20261027-quality-final/`，不能混成原本全套同一版本通過的證明。
