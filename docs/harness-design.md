# 自寫 agent-harness 設計取捨

用途：動手寫核心之前，先決定各家 harness 有的功能「我們要不要、放哪裡」。目標是集各家優點、去掉缺點、保持輕量。本文是階段 0 的成果，階段 1 起的程式與測試都照這裡。

本文每項行為標明三種狀態：**已實作**（讀過程式或測試，2026-11-01 核對）、**待實作**（本文定下的目標，尚無程式）、**待驗證**（無法從程式或測試確認）。方向不變：單一核心迴圈、輕量核心、MCP 工具走 `Tool` 介面、持久化由平台層負責。

## 名詞

- 場次（session）：一段對話的完整紀錄，可以存檔、接著跑、重建。Agent 每次執行都屬於某個場次。
- 回合（turn）：一次模型呼叫，加上該次要求的工具執行。整次執行（run）由多個回合組成。
- 回呼（callback）：核心在特定時間點呼叫外部程式。Claude Agent SDK 有三種：問權限（can_use_tool）、掛勾（hook）、內建 MCP 的呼叫。我們只留一種：Hook。權限與掛勾合併；MCP 不是回呼，是「工具的來源」。
- MCP：讓外部程式提供工具給 Agent 的標準協定。
- 結果未知（OutcomeUnknown）：工具已派出，但無法確認外部操作是否發生。它不是失敗，也不是成功。

## 輕量的量化界線

- 核心 crate `agent-harness` 不碰檔案、網路、資料庫；只依賴非同步與取消的基本套件。
- 1,500 行與 20 個公開名稱是**觸發設計審查的門檻**，不是硬性禁令。達門檻時先檢查責任邊界，再決定是否拆 crate。現況（2026-11-01 實測）：`crates/harness/src` 共 460 行；`lib` 匯出 20 個名稱。已檢查新增的 `ModelReply` 與 `TurnStatus`：分別承載模型回覆及回合狀態，供核心和轉接層共同使用；尚無需要拆成另一 crate 的獨立責任，暫維持原邊界。
- 目前沒有自動擋公開名稱增加的檢查（`crates/xtask/src` 查無相關程式）；舊版文件寫「有公開面積檢查」與事實不符，已更正。是否引入 `cargo public-api` 之類工具：待驗證。
- 以類別（型別）為單位管理：內聚性高的程式放同一檔，型別連同它的方法放同檔。這取代舊版「一檔一個函式」；使用者 2026-11-01 定，`AGENTS.md` 已同步。
- 每項功能都要有可驗收的行為或不變條件。只有主打的差異化能力，才要求跨產品實測比較。

## 核心保證（先分清兩種，不可混為一談）

1. **每個 call_id 只有一筆終局結果。** 這是核心與 SessionStore 要保證的事。
2. **外部操作只執行一次。** 核心保證不了。不同 call_id 可能代表同一筆業務操作（模型重新發出一次下單），只靠 call_id 擋不住重複下單。

結果未知的副作用操作，處理順序：工具有查詢能力就先對帳；有可靠的業務冪等鍵才可安全重送；否則停止自動重做，交由人處理。

## 工具呼叫與結果配對

規則（待實作的完整版）：

- 以「完整接收並接受」的 call_id 為單位。半截的串流參數不算已接受。
- 核心交給模型的下一輪歷史中，每個已接受的呼叫必須恰有一筆結果，不多不少。
- 同一批工具遇到取消時逐筆結算：已完成者保留原結果；尚未派工者記為「未執行」；已派工者依實際可確認的狀態回報，確認不了就記結果未知。
- 程序在外部副作用發生後、結果落盤前崩潰，恢復時記為結果未知，不當成工具失敗。重複恢復不得新增第二筆終局結果（同一 call_id 的終局結果寫入須冪等）。

現況（已實作，`crates/harness/src/agent.rs`、`tests/run.rs`）：

- 同一批呼叫**依序**逐一執行，沒有平行派工。
- 壞參數、未知工具、被 Hook 略過、工具失敗各產生一筆結果並回報模型。重複 call_id 在接受回覆前拒絕整批，不執行該批工具；也拒絕重用先前回合的編號（測試 `duplicate_call_id_rejects_the_batch_before_any_dispatch`、`reused_call_id_in_later_turn_is_rejected_before_dispatch`）。
- 工具執行中收到取消即丟棄該工具（測試 `cancel_during_a_slow_tool_stops_it_before_it_writes`）。邊界：已進入同步阻塞寫入的工具無法中斷。

與目標的差距：

- 核心取消時回傳歷史：已完成結果保留，派工中無法確認的結果記為「結果未知」，尚未派工記為「未執行」。CLI 外層目前仍可先中止核心，未保存這份歷史；持久化與接續屬階段 1B。
- 沒有 OutcomeUnknown 型別。任務紀錄層（`crates/agent`）對「已派發、沒有回執」的動作有結果未明的標記，測試 `dropped_connection_after_dispatch_is_not_dispatched_again_and_finish_marks_unknown` 只涵蓋連線中斷，且收尾要人呼叫 `finish()`；崩潰後自動收尾沒有（見 `docs/aar-h5-simulation.md`）。

## 模型回合與整次 run 的停止語意

兩件事分開看：

- **模型這一輪回了什麼**（回合狀態，由模型 adapter 判讀供應商的停止原因）：自然完成、要求工具、需要續接、輸出截斷。
- **整次 run 為什麼停止**（run 終止原因）：自然完成、截斷、輪數耗盡、取消、整次 run 被政策攔截、致命錯誤。

「要求工具」與「需要續接」只是回合狀態，不是 run 的終止原因。

規則：

- 不再以「模型沒有要求工具就視為正常完成」判斷結束。是否自然完成，看 adapter 回報的停止原因。
- 續接（供應商回覆要求繼續）必須有次數上限，超過算截斷或輪數耗盡，不得無限續。
- 呼叫端必須能區分上列六種終止原因。單一工具被拒絕或失敗，仍回報模型並繼續，不算 run 終止；只有政策明確要整次攔截才終止。
- 優先相容既有 `RunError`，新增的公開型別數量不在本文硬定，實作時以最小改動為準。

現況：

- **已實作**：`RunError` 區分取消（附歷史）、回合上限、截斷、模型政策攔截、模型失敗與掛勾停止；成功回 `RunOutput` 代表自然完成。
- 核心依 `ModelReply` 回合狀態決定是否完成；續接受回合上限約束，狀態與工具呼叫不一致會報錯且不派工。
- `crates/openai` 判讀 `stop`、`tool_calls`、`length`、`content_filter`；原因缺失或不認識時報錯。此轉接層未定義供應商續接原因，核心續接分支由假模型測試。
- 輪數上限（預設 8）、取消在模型呼叫前與中、取消在工具執行前與中：已實作。

## 未知內容的處理

- 核心只需理解文字與工具呼叫。
- adapter 必須保留供應商要求「下一輪原樣帶回」的內容（例如推理區塊的簽章資料）；核心視為不透明資料，原樣存、原樣回。若某供應商的內容無法安全續接，adapter 明確回報不支援，不靜默丟棄。
- 場次恢復後也要滿足同一條件：重放用的紀錄必須含這些原樣內容。只寫除錯日誌不足以支援重放。
- 這次不擴張成完整多模態設計；圖片等在接多家模型前再訂。

現況：`Message` 只有文字與工具呼叫，沒有放不透明內容的欄位；`read_reply` 讀不到的欄位目前會被略過，沒有記錄。整項待實作。供應商是否真要求原樣帶回、各自格式：待驗證（本文未逐家核對原始文件）。

## Hook 與批准

- 階段 1 只保留兩個 Hook：工具派工前（可放行、略過、停止）、結果後（可放行、停止）。現況已實作，見 `crates/harness/src/hook.rs`。
- 這兩個觀測點可以偵測**重複的工具呼叫**；**看不到沒有工具呼叫的模型續接迴圈**，後者由核心的續接上限與輪數上限兜底。
- 批准遭拒：只把該工具記成「被拒絕」回報模型，run 繼續（使用者 2026-11-01 定；理由：人工拒絕少見，多數拒絕來自模型，不必為此結束整個任務）。批准服務故障：視為拒絕，屬基礎設施故障，仍整次停止。兩者之後的 Hook 都不得重新放行。現況：人工拒絕回 `Skip`，核心回報模型並繼續；資料服務故障仍回 `Stop`。假模型與 CLI 測試確認拒絕不派工且下一次模型請求收到結果。
- 結果後 Hook 發生錯誤（回 `Stop`）時，必須另行記錄錯誤，**不能覆寫已知的工具結果**。現況：`handle` 在 `on_outcome` 回 Stop 時直接回傳 `Err(Stopped)`，工具結果（訊息）被丟掉、沒有另記；屬待實作。
- 不為尚未實作的擴充預先增加 Hook（模型前後、迴圈偵測等需要時再加）。

## 要避開的反例

- 同時有多套迴圈（Gemini 四套），行為會分歧：核心只有一個迴圈。
- 終止靠例外，各管線吞法不同（MAF）：停止原因用列舉，不用例外。
- 空回覆重試與續接沒有次數上限（Gemini）：所有重試與續接都要有上限。
- 只用除錯用的斷言保證「同時只有一個回合」（Codex）：要用正式檢查並有測試。
- 只寫入、不強制落盤（三家都沒有 fsync）：場次寫入要定義落盤時機並測試崩潰。
- 把「call_id 唯一」說成「操作只做一次」：不同 call_id 可代表同一筆業務操作。
- 結果後 Hook 出錯就丟掉已知的工具結果：錯誤與結果分開記。
- 只把供應商的不透明內容寫進除錯日誌：重放時就不完整。

## 對現有程式的影響

- 現況（已實作）：`Agent::run` 吃一句提示、回傳訊息與文字；停止原因由 `ModelReply` 判讀，取消錯誤帶歷史；壞參數回報模型、呼叫與結果配對、重複 call_id 整批拒絕、工具執行中取消，均已有測試。沒有場次、沒有 MCP、沒有不透明內容欄位。
- 階段 1A（不依賴持久化，只改核心與假模型測試）：
  - 以可控的假模型與假工具驗證壞參數、工具結果配對、停止原因（含回合狀態與 run 終止原因分開），以及批次工具在「已完成／執行中／未派工」三種狀態下遇到取消。
  - 測試維持依序派工，不得暗自引入平行派工需求。
  - 驗收：每種狀態的結果各一筆且與歷史配對；取消後歷史完整可交給模型；刪除「無工具呼叫即完成」後舊測試改以停止原因驅動。
- 階段 1B（持久化）：
  - 做 `SessionStore` 契約、一致性測試，以及平台層（SQLite）實作。
  - 驗收一：「已開始」寫入失敗時，副作用工具的派工次數為 0。
  - 驗收二：模擬外部操作已成功、結果尚未落盤時強制終止（真的殺程序，不只關閉連線），連續恢復兩次後，外部操作沒有被自動重做，終局結果也沒有重複。
