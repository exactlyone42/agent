# mortal agent：有身分與目標的 Agent

用途：說明這個專案新一代 Agent「mortal agent」長什麼樣、為什麼這樣分、每個優先級判斷用什麼算法。圖形成品見 [架構圖 PDF](mortal-agent-architecture.pdf)，共 4 頁（圖仍是 2026-11-16 版，還用 `Person` 與編譯期組裝，要依本文更新，見第六節）。實作步驟在 [PLAN.md](../PLAN.md)「mortal agent 實作步驟」，工作紀錄格式在 [records.md](records.md)。文中 M1–M7 是那份實作步驟的編號，P05 這類 P 開頭的編號是 PLAN.md 的階段。

目前狀態（2026-11-17）：本文是設計，沒有改任何程式，沒有花費，沒有動到正式環境。`capabilities` 與 `scheduler` 兩個 crate（Rust 的程式套件）尚未建立。2026-11-17 起，能力載入、優先級、命名與比賽目標四項決策已定案（見下節），本文已依決策改寫；決策之外的舊內容只在不衝突時保留。

## 已定案的決策（使用者 2026-11-17 定）

1. 能力載入：用「登記處（Registry）加解析器（Resolver）加綁定（Binding）」，分四個階段，Run 開始時建立有版本的能力快照，現在只實作凍結政策。
2. 急迫性與重要性分開算，外部請求只能提出主張，不能決定優先級；優先級由確定的政策算出。
3. 命名：核心型別叫 `MortalAgent`，不再用 `Person`；Pinocchio 只當實例名或專案代號。
4. 近期首要目標是 Google PLE 比賽，爭取前三名；比賽版全自動、不靠人工批准；長任務用「主控加短生命週期工人」。

這四項取代本文 2026-11-16 版的對應內容，包括：編譯期組裝取代執行時載入、急與重要由請求者填、型別叫 `Person`、比賽版只是候選用途。

## 一句話

mortal agent 是「擬人化」的 Agent（讓大型語言模型自己決定下一步，必要時呼叫工具來完成工作的程式）：它像一個人，有**身分**（我是誰、職責是什麼）和**目標**（現在要完成什麼），手上拿著這件工作的**上下文**（到目前為止的對話紀錄）。迴圈、工具呼叫、排程、驗證、協調工人、檢索資料這些本領，統一叫「**能力**」。

專案名與 repo 名不改，仍是 Agent Platform；mortal agent 是這個 Agent 的設計名稱（使用者 2026-11-16 定）。

能力不是 Agent 身上的開關，而是 Agent 取得資格後，由解析器按任務需要選進來的東西：沒取得資格就沒有，取得了也不是每次都用。Agent 核心不引用任何能力的實作，只記「我有哪些能力的綁定」；能力的程式才引用核心，所以兩邊可以分開開發、分開測試。

## 一、現況與目標

現況（2026-11-16 讀程式確認，2026-11-17 文件改寫時未改程式）：

- `cli` 收命令，交給 `agent` crate 的任務流程（輸入檢查、把任務存進 SQLite 這個單檔資料庫的任務庫、驗證）。
- 任務流程在 `crates/agent/src/task.rs:222` 組出 `harness`（本專案自寫的 Agent 核心套件）的 `Agent`：模型、Hook（工具執行前後可插入判斷的掛勾）、兩個工具（讀輸入的 `ReadInput`、寫輸出的 `WriteOutput`）。
- `Agent::run` 一個函式同時管迴圈、呼叫模型、執行工具與問 Hook，這幾件事綁在一起，拆不開。
- 批准閘門在 `approval` crate，實作 `Hook`。模型連線在 `openai` crate，連到另一個 repo 的 Gateway（對外提供 OpenAI 相容介面的模型閘道）。
- 沒有排程：一個任務就是一次 `run`，沒有收件匣（排隊等候的任務清單）、沒有優先級、沒有依賴。
- 沒有能力的登記處、解析器、快照，也沒有 `MortalAgent` 型別。

目標：

- `harness` 只留 Agent 核心：`MortalAgent`、`Work`（一件工作與它的對話紀錄）、`Capability` 介面、`CapabilityBinding`，以及既有的 `Model`、`Tool`、`Hook`。
- 新 crate `capabilities` 放迴圈與工具呼叫兩項能力，也放登記處、解析器與快照；新 crate `scheduler` 放排程能力。
- `agent` 負責把核心、能力與任務庫組起來；`approval`、`openai`、`cli` 不動。
- 驗證、協調工人、檢索資料都是之後各自獨立的能力，不放進 `MortalAgent`。

## 二、能力

### 命名與核心

核心型別叫 `MortalAgent`，不叫 `Person`（使用者 2026-11-17 定）。Pinocchio 只可作為某個 Agent 實例的名字或專案代號，不寫死成通用型別，避免架構語意不清。

核心草稿如下，實作時以編譯結果為準：

```rust
pub struct MortalAgent {
    pub id: AgentId,
    pub identity: AgentIdentity,
    pub goals: Vec<Goal>,
    pub capabilities: Vec<CapabilityBinding>,
}
```

核心只知道自己綁了哪些能力（`CapabilityBinding` 是登記資料，不是能力的程式），不知道能力怎麼實作。上下文放在每件 `Work` 裡，不放在 `MortalAgent`。

核心有三個基本動作：聽（收到任務）、想（呼叫模型一次）、說（交出回覆），另有一條底線：隨時可以被叫停。核心不含：

- 迴圈、工具執行、批准流程。
- 任務優先級計算、重試與恢復策略。
- 長期記憶、特定模型的介面、具體的工具實作。
- 比賽專屬規則。

這些放在能力、`AgentRuntime` 或轉接層。`AgentRuntime` 目前只定義三件事：需要時啟用能力、傳遞取消訊號、執行一次 Run；預算、副作用控制與狀態歸誰管，還沒定案（第六節）。模型由 `MortalAgent` 還是 `AgentRuntime` 持有，也留到 M1 做原型時決定。

### 能力的四個階段

| 階段                | 意思                                                                | 誰負責         |
| ------------------- | ------------------------------------------------------------------- | -------------- |
| 可用（Available）   | 系統已經登記了這項能力                                              | 登記處         |
| 已取得（Acquired）  | 這個 Agent 有使用資格                                               | 授權與設定管理 |
| 已綁定（Bound）     | 解析器依任務需求、Agent 目標、能力依賴與授權政策，決定這次 Run 要用 | 解析器         |
| 已啟用（Activated） | 真正需要時，由執行環境把能力初始化並開始用                          | `AgentRuntime` |

取得資格不等於每次都用：只是單次問答的工作，不需要綁工具呼叫。

### 解析器怎麼決定

解析器是確定性的程式，同樣的輸入一定得到同樣的結果，不由模型決定。輸入有四項：任務需求、Agent 的目標、能力之間的依賴、授權政策。輸出是這次 Run 的綁定清單。

- 依賴缺少、依賴循環、授權不符：在組裝階段拒絕，並說明原因，不默默少載一項再執行。
- 模型可以建議「某項能力可能有用」，但不能因此取得新權限；不存在讓模型自己加能力或加權限的呼叫。
- 任務需求對應哪些能力，由登記處的宣告與政策決定，不寫死在核心。

### 能力快照與政策

Run 開始時建立一份有版本的能力快照，記錄：用了哪些能力、各自的版本、設定、解析結果。

- **凍結政策（Frozen）**：整個 Run 都用同一份快照。目前只實作這個。
- **動態政策（Dynamic）**：只在安全邊界才能換快照，每次換都產生新版本。架構要能容納，但現在不實作。

動態變更要留下紀錄：變更前後的版本、原因、新增與移除的能力、依賴與授權的結果、從哪一步開始生效、對正在等待的操作有沒有影響。工具做到一半時，不能移除它需要的執行與恢復能力。

安全邊界分兩種，不能混用：取消檢查點（停止安排後續動作）、重組檢查點（可以安全地換能力組合或換工作）。到重組檢查點時，目前狀態必須已寫入，未完成的操作必須追得到。

### 停用、解除綁定、撤銷授權

三件事不同，不能混淆：

| 操作               | 時機                                 | 意思                                       |
| ------------------ | ------------------------------------ | ------------------------------------------ |
| 停用（Deactivate） | 能力暫時沒有工作，且沒有未完成的操作 | 釋放執行資源，狀態保留                     |
| 解除綁定（Unbind） | Run 結束，或到合法的重組檢查點       | 從這次 Run 的能力組合移除                  |
| 撤銷授權（Revoke） | 授權被收回                           | Agent 失去使用資格；立刻擋住新的受保護操作 |

- 能力暫時沒有事件，不能因此刪掉它的狀態。
- 有未完成的工具呼叫、待處理的副作用或恢復工作時，不能銷毀必要資訊。
- 已開始的操作怎麼收尾，依取消與副作用的契約；取消不代表副作用已回復。
- Run 結束可以釋放能力的實例，但執行紀錄要留。

### 能力怎麼包

能力一層包一層，每一層都實作同一個介面 `Capability`，意思是「做一次工作」：

1. 最內層是核心：想一次。
2. 往外是**工具呼叫**：想完後，執行模型要求的工具，把結果放回上下文。
3. 再往外是**迴圈**：還有結果等模型回覆，就再想一次，直到做完或超過回合上限。
4. 最外面是**排程**：同時有好幾件任務時，決定先交哪一件給裡面那疊能力。排程管「多件工作之間」，其他能力管「一件工作之內」，所以排程持有那疊能力、一次交一件進去，不是被包在裡面。

批准閘門不是獨立一層，它是工具呼叫的前置檢查，現有的 `Hook` 就是它，`approval` crate 不用改。

草稿如下，實作時以編譯結果為準：

```rust
pub trait Capability: Send + Sync {
    fn run(
        &self,
        work: &mut Work,
        cancel: &CancellationToken,
    ) -> impl Future<Output = Result<(), RunError>> + Send;
}

let agent = Loop::new(8, ToolCalling::new(tools, hook, core));
```

`run` 收一件工作和一個取消訊號（`CancellationToken`，外面可用它通知「請停止」）。最後一行由內往外讀：核心包上工具呼叫，再包上迴圈；8 是回合上限（現有程式的預設值也是 8）。

**和 2026-11-16 版的差別（使用者 2026-11-17 改）**：舊版選編譯期組裝，放棄執行時載入；新版要求登記處加解析器加快照。取捨如下：

- 得到：能力按需求載入，不同任務可以用不同組合；比賽可以一次換掉一項能力做對照實驗；新增能力不用改核心。
- 失去：舊版靠型別在編譯時擋掉「沒有工具呼叫就接不上批准」這類組裝錯誤，新版有一部分要改到解析階段才擋。
- 補救：每項能力要求的依賴寫進登記處，解析器在組裝時檢查；`ToolCalling::new` 仍把 `hook` 當必填參數，所以工具呼叫本身接不上批准的情況仍編譯不過。
- 還沒驗證：登記處的執行時清單，如何與上面的泛型包法合在一起（例如用一個組裝函式表，依快照建出那疊能力）。這要等 M2 做原型才知道，實作時以結果為準；現有程式也是這個分工：`Hook` 用泛型，只有要放進清單的 `Tool` 才用 `Box`（`crates/harness/src/tool.rs` 的 `ToolFuture`）。

核心與能力分開的規則不變：核心所在的 crate 不依賴任何能力，能力的 crate 依賴核心，方向只有一個。這條規則要寫成 `cargo xtask gate`（本專案的自動檢查命令）的檢查，不只靠文件。

## 三、優先級與排程：每個判斷用什麼算法

原則（使用者 2026-11-16、2026-11-17 定）：優先級的判斷全部由程式與算法做，不由模型估；同樣的輸入一定得到同樣的順序。排程是一項能力（排程能力），不寫死在 `MortalAgent` 核心。每個算法在實作前先寫在這裡，包含放棄的做法與代價。

### 輸入從哪來

急迫性與重要性**分開計算**，兩者都由 `PriorityPolicy` 用可信資料算，外部請求只能附上 `PriorityClaim`（它自己說的急與重要），不能直接決定 `EffectivePriority`（有效優先級）。

- **急迫性（Urgency）**：依可信的截止時間（Deadline）、服務水準協議（SLA，事先約定的處理時限）、剩餘時間、可信監控回報的事件嚴重程度。剩餘時間每次重選都重算，同一件事可能因為時間逼近而變急。
- **重要性（Importance）**：依 Agent 的目標、這件工作綁到哪個目標（Goal Binding）、任務影響、硬依賴（別的重要工作必須等它）。
- **不可信的來源**：外部訊息自己宣稱重要，不算數；只有 `PriorityClaim` 被可信規則（例如授權政策明確允許某來源提高優先）承認時，才影響結果。
- **沒有資料時**：沒有可信的截止時間，就當不急；任務影響來源沒有可信資料，就當沒有影響，不由模型補。這是本文暫定的保守規則，還沒對使用者確認（第七節）。

「急」的門檻（剩幾分鐘算急、哪一級嚴重度算急）是 `PriorityPolicy` 的參數，數值未訂，實作前要訂並寫進這裡。

### 選下一件事的步驟

1. **驗證授權與硬性約束**：沒有授權、超過預算、違反硬限制的任務，直接拒收並回報原因，不進入比較。
2. **檢查身分與目標是否一致**：不在這個 Agent 職責與目標內的任務，拒收並回報原因。
3. **建立並驗證依賴圖**：任務依賴圖必須是 DAG；有循環就拒收並列出循環。
4. **選出可做的任務（Ready Works）**：只留前置任務都已完成的任務。
5. **比較重要性與急迫性**：算出每件任務的象限（見下表），再做優先級繼承，得到有效象限（EffectivePriority）。
6. **比較解鎖價值（Unlock Value）**：做完這件，能讓多少重要、在關鍵路徑上的任務變成可做。
7. **比較可信的預估成本**：成本估計來自歷史資料或已知的工具成本。
8. **最後用先來先做（FIFO）**：收件序號小的先做。

控制命令（第一版只有「取消」）與任務放同一個收件匣，比較鍵第一項是類別，控制命令排在任務前。

象限編號，數字小的先做：

| 編號 | 象限         |
| ---- | ------------ |
| 0    | 急且重要     |
| 1    | 重要不急     |
| 2    | 急不重要     |
| 3    | 不急也不重要 |

執行規則：這件做完才重選；執行中新來的任務只進收件匣，不搶占；取消例外。每次選擇留一筆紀錄：選了誰、候選有哪些、各自的象限與有效象限、是哪一項決定了順序。

第 6、7 步的狀態：

- 順序已定案，但**算法還沒設計、也沒實作**。解鎖價值要先寫出「什麼算解鎖」「關鍵路徑怎麼算」的算法與取捨；成本估計要先有歷史資料來源。
- 資料不足時，不得用虛構的數字影響排序：任何一方的成本未知，這一項視為平手，交給下一項。
- 成本估計不可靠時，不得凌駕明確的優先級（第 5 步）。

### 範例

A（重要不急，象限 1）要等 B（不重要也不急，象限 3）先完成；C 是急但不重要（象限 2）。一開始只有 B 與 C 可做，A 還在等 B。

- 不做繼承：B 是 3，C 是 2，C 先、B 次之；A 要等 B 做完才能做，等於被拖到最後。
- 做繼承：B 繼承 A 的象限，變成 1，比 C 的 2 先。B 做完後，A（1）又比 C（2）先，所以順序是 B、A、C。

### 關於「分叉」

分叉指做完 A 之後，有幾件事可以接著做，也就是後繼數。做完 A 只有 B 可做時，後繼數是 1，這是允許的。「0 分叉」（沒有多出來的分支）與「出度 1」（圖論用語，從 A 往外連出 1 條箭頭）是同一件事的兩種數法，本文統一用後繼數。後繼數不直接拿來排序；解鎖價值要看解鎖的任務是否重要、是否在關鍵路徑上、是否真的因此變成可做。

### 資料與檔案

- 型別連同它的方法放同一檔（使用者 2026-11-01 改，取代 2026-10-28「獨立函數一檔一個」）：`Request`（含 `PriorityClaim`）、`Task`、`PriorityPolicy`、`EffectivePriority`（算出象限編號的 `quadrant()`）、`Inbox`（收件匣，負責發遞增序號）、`Decision`（一次選擇的紀錄）。
- 選擇流程的函式（`select_next`、`ready_tasks`、`propagate_priority`、`find_cycle`、`passes_filters`）依內聚性放在同一份或相近的檔案，不為了一檔一函式而拆。
- 檔案放在 `scheduler` 的 `src/`。

### 第一版不做

- 步驟邊界重排、暫停、繼續、重試。
- 解鎖價值與成本比較的算法（順序已訂，算法未設計）。
- 跨 Agent 的請求：多個目標就開多個 Agent，各自有收件匣；別的 Agent 送來的訊息，當成一般請求。
- 比賽版不用排程，見第五節。

## 四、harness 功能取捨

動手寫核心之前，先決定各家 harness（管模型、工具、授權與接續的 Agent 外殼）的功能「我們要不要、放哪裡」。目標是集各家優點、去掉缺點、保持輕量。證據來源是 `harness-study` 的 Claude Agent SDK、Codex、Gemini CLI、Google ADK、DeerFlow、Microsoft Agent Framework（下稱 MAF）六份模組版 PDF，與 topics 七份比較；各家文件寫「文件未載」的地方，本表也是未查證。

名詞：場次（session）是一段對話的完整紀錄，可存檔、接著跑、重建。回呼（callback）是核心在特定時間點呼叫外部程式；我們只留 `Hook` 一種。MCP 是讓外部程式提供工具給 Agent 的標準協定，它是「工具的來源」，不是回呼。

輕量的量化界線（本專案自訂的判斷，不是來源數字；階段 1 結束時用實測行數檢討）：

- 核心 crate `harness` 不碰檔案、網路、資料庫；只依賴非同步與取消的基本套件。
- 核心程式碼不超過 1,500 行（2026-10-28 現況 296 行）。超過就把功能拆成獨立 crate。`capabilities` 與 `scheduler` 先套用同一條線。
- 核心對外匯出不超過 20 個名稱（2026-11-17 定案的命名會超過，見第二節與第七節）。能檢查對外介面大小的工具（如 `cargo public-api`、`cargo semver-checks`）是否可用於本專案，未查證。

放哪裡的三種答案：**核心**（在 `harness`）、**能力**（在 `capabilities` 或 `scheduler`，或之後各自的 crate）、**擴充**（有需要才做的獨立 crate）。

要避開的反例：

- 同時有多套迴圈（Gemini 四套），行為會分歧：只有一個迴圈能力。
- 停止靠丟例外，各處理流程接住例外的方式不同（MAF）：停止原因用列舉，不用例外。
- 模型回空內容時重試，沒有次數上限（Gemini）：所有重試都要有上限。
- 只用除錯用的斷言（只在開發時檢查）保證「同時只有一個回合」（Codex）：要用正式檢查並有測試。
- 只寫入、不強制落盤（三家都沒有 fsync，即要求作業系統把資料真正寫進磁碟）：場次寫入要定義落盤時機並測試崩潰。

做的順序：

- 階段 1 先做：壞工具參數回報模型（現在會中止整個任務）、呼叫與結果配對鐵則、停止原因列舉（成功結束也要有原因）。
- 場次介面與一致性測試排在階段 1 之後、接上真正的 Gateway 之前，因為續跑與取消接續都依賴它。
- 現況（2026-10-28 讀程式）：`Agent::run` 吃一句提示、回傳訊息與文字；停止只靠 `RunError` 四種；沒有場次、沒有成功端的停止原因、沒有 MCP。
- 六份模組版文件多處標「文件未載」：Gemini 場次儲存細節、ADK 與 MAF 的匯出清單、DeerFlow 停止條件，未回原始碼核對。

## 五、比賽版（PLE）：近期首要目標

使用者 2026-11-17 定：近期首要目標是 Google PLE Agent Harness 比賽，爭取前三名。取代 2026-11-16 版「候選用途，尚未決定參加」。

PLE 是 Google 與 Mercor 的工程題自動做題比賽。官網 ple-bench.com（2026-11-17 讀）列的比賽期間是 2026-11-09 至 2027-01-05，前三名獎金 25 萬、10 萬、5 萬美元，每組「執行框架（即 harness）加模型」在不公開的隱藏題上跑 3 次。

評分分兩種。以限制與設計目標評分的題，每個交付項的分數是 `s = 0.4p + 0.6·G·O'`（p、G、O' 各代表什麼，本文未查證），硬性限制破任何一條，該項最高只剩 0.4 分。其他題由 LLM（大型語言模型）評審對照評分標準打分。兩者都出自官方 `docs/rules.md`。

本節目前是設計，沒有比賽版程式，沒有跑過任何比賽題，沒有花費。

### 比賽的約束

- 全自動：比賽每題一個全新容器（隔離的執行環境），最長 6 小時，沒有人批准、沒有桌面畫面，要接比賽方規定的 WebSocket（網路上的雙向即時連線）協定。比賽版不依賴人工批准。
- 多來源收件匣與多目標排程屬於可擴充能力，不是比賽的必要依賴；比賽版一次一題，不載排程。
- 協調工人與檢索資料（RAG）是可選能力，不內建到 `MortalAgent` 核心；比賽版載不載，由消融實驗的結果決定。
- 現有 Agent 不能直接拿去比賽：要接比賽協定，要補下面的新部件。
- 效能優先看泛化能力、正確率、成本與可驗證性，不針對公開題調整；公平競賽規則（不寫死答案、不讀評分程式、只連模型主機、不外傳題目內容、模型名從環境變數讀）各要配一項自動檢查（目前尚未實作），規則原文在 google-research/ple 的 `docs/rules.md` 與 `kit/README.md`。

### 長任務模式：主控加短生命週期工人

這是本專案目前重視的長任務執行方式，用一項可選的協調能力（Orchestration）實現，不是核心的一部分。

- 主控只依賴四樣東西：原始的目標契約（Goal Contract）、最新進度、已驗證的成果、剩餘工作。主控不持續累積工人的完整對話，也不靠有損的記憶壓縮來維持目標。
- 工人每次拿到一份明確的工作契約、必要的能力與局部的上下文，做完就結束。
- 工人結束時交回成果與證據；進度由獨立的驗證結果更新，不由工人自己宣稱完成。
- 主控每次都根據最新的權威狀態，重新決定下一步。

和既有設計的關係：驗證才算成功，已是本專案的規則（AGENTS.md）。第四節把子代理與記憶放在核心之外，這裡一致。第四節的「壓縮」只是擴充，主控設計不依賴它。

這個模式是否真的比單一 Agent 好，**還沒有實測**。PLAN.md 也寫了沒有實測前，不得宣稱平行比單一 Agent 快或更好。要靠消融實驗證明。

### 比賽版的組合與新增部件

- 載入：`MortalAgent` 加迴圈加工具呼叫加「檢查員」（交件前逐條對照題目要求）；可選載入協調能力。不載批准與排程。
- 新增部件：協定層（`exec`、`read_file`、`write_file`、`http` 四種請求）、檢查員、先交件、時間預算。保留任務迴圈與模型連線；批准、任務庫、桌面、知識庫不用。
- 比賽程式放獨立 GitHub repo；需要的兩個 crate 用複製的方式帶過去，因為比賽建置時是不帶帳號的匿名複製，拉不到私有 repo 的子模組（git submodule，repo 內嵌的另一個 repo）。要不要建這個 repo 還沒定（第七節）。

### 消融實驗

消融實驗是一次只換掉一個部件，其餘不動，看分數掉多少。每一組對應一個組裝設定（Capability Snapshot）：A0 全載、A1 無檢查員、A1n 檢查員照跑但一律放行（負向對照：檢查員形式上還在，但失去作用）、A2 無先交件、A3 無時間意識、A4 規劃執行檢查三角色、A5 預算三檔、A6 結尾不附證據、A7 換模型。新增主控加工人與檢索兩組：A8 單一 Agent 對主控加工人、A9 有無檢索。每次執行都要留下能力快照，才能證明當時載入了什麼。

事實來源：google-research/ple 的 README 與 docs（rules、protocol、models、artifacts）、`kit/README.md`、`eval/README.md`、`eval/dev_set.yaml`，以及 Mercor 2026-11-03 的部落格。

還沒查證：

- 有沒有書面報告：官網與官方 repo 都沒提；先前記的配分（25／25／15／20／15）只來自使用者貼文，Kaggle 頁面讀不到，視為未證實。
- 程式可讀性是否計分，找不到原文；官網只寫效能計分。
- 隱藏題的排名方式、成本是否計分，官方 repo 寫「之後公布」；提交截止的確切時點，官網只列比賽期間，未單獨標示。
- Rust 能否在比賽的建置環境編譯：官方建置映像（debian:bookworm，預先做好的系統環境）附編譯器，`install` 步驟可上網，最長 30 分鐘；但文件沒寫有 Rust 工具鏈，需在 `install` 裝，並用官方 kit 實測。現有模型連線能否接比賽的模型代理，也還沒試。
- 一次完整開發集實跑的時間與費用還沒量；跑開發集要花模型費用，需要使用者同意後才跑。
