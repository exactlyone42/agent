# mortal agent：有身分與目標的 Agent

用途：說明這個專案新一代 Agent「mortal agent」長什麼樣、為什麼這樣分、每個優先級判斷用什麼算法。圖形成品見 [架構圖 PDF](mortal-agent-architecture.pdf)，共 4 頁。實作步驟在 [PLAN.md](../PLAN.md)「mortal agent 實作步驟」，工作紀錄格式在 [records.md](records.md)。文中 M1–M7 是那份實作步驟的編號，P05 這類 P 開頭的編號是 PLAN.md 的階段。

目前狀態（2026-11-16）：本文是設計，沒有改任何程式，沒有花費，沒有動到正式環境。`capabilities` 與 `scheduler` 兩個 crate（Rust 的程式套件）尚未建立。

## 一句話

mortal agent 是「擬人化」的 Agent（讓大型語言模型自己決定下一步，必要時呼叫工具來完成工作的程式）：它像一個人，有**身分**（我是誰、職責是什麼）和**目標**（現在要完成什麼），手上拿著這件工作的**上下文**（到目前為止的對話紀錄）。迴圈、工具呼叫、批准、排程這些本領，統一叫「**能力**」。

專案名與 repo 名不改，仍是 Agent Platform；mortal agent 是這個 Agent 的設計名稱（使用者 2026-11-16 定）。

能力不是人身上的開關或設定值，而是人學不學的事：沒學就沒有，學了才有。人的程式不引用任何能力，能力的程式才引用人（見第二節的依賴方向），所以人與能力可以分開開發、分開測試。

## 一、現況與目標

現況（2026-11-16 讀程式確認）：

- `cli` 收命令，交給 `agent` crate 的任務流程（輸入檢查、把任務存進 SQLite 這個單檔資料庫的任務庫、驗證）。
- 任務流程在 `crates/agent/src/task.rs:222` 組出 `harness`（本專案自寫的 Agent 核心套件）的 `Agent`：模型、Hook（工具執行前後可插入判斷的掛勾）、兩個工具（讀輸入的 `ReadInput`、寫輸出的 `WriteOutput`）。
- `Agent::run` 一個函式同時管迴圈、呼叫模型、執行工具與問 Hook，這幾件事綁在一起，拆不開。
- 批准閘門在 `approval` crate，實作 `Hook`。模型連線在 `openai` crate，連到另一個 repo 的 Gateway（對外提供 OpenAI 相容介面的模型閘道）。
- 沒有排程：一個任務就是一次 `run`，沒有收件匣（排隊等候的任務清單）、沒有優先級、沒有依賴。

目標：

- `harness` 只留「人」：`Person`、`Work`（一件工作與它的對話紀錄）、`Capability` 介面，以及既有的 `Model`、`Tool`、`Hook`。
- 新 crate `capabilities` 放迴圈與工具呼叫兩項能力；新 crate `scheduler` 放排程。
- `agent` 負責把人、能力與任務庫組起來；`approval`、`openai`、`cli` 不動。

| 工具呼叫             | `agent.rs:116` `handle`    | `capabilities` 的 `ToolCalling`  | 第 2、3 頁 |

## 二、能力

### 人與能力

人有三個基本動作：聽（收到任務）、想（呼叫模型一次）、說（交出回覆）。另有一條底線：隨時可以被叫停。人手上帶三樣資料：身分、目標、上下文。

能力一層包一層，每一層都實作同一個介面 `Capability`，意思是「做一次工作」：

1. 最內層是人：想一次。
2. 往外是**工具呼叫**：人想完後，執行模型要求的工具，把結果放回上下文。
3. 再往外是**迴圈**：還有結果等模型回覆，就再想一次，直到做完或超過回合上限。
4. 最外面是**排程**：同時有好幾件任務時，決定先交哪一件給裡面那疊能力。排程管的是「多件工作之間」，其他能力管「一件工作之內」，所以排程自己持有那疊能力、一次交一件進去，不是被包在裡面。

批准閘門不是獨立一層。它是工具呼叫的前置檢查，現有的 `Hook` 就是它，`approval` crate 不用改。

草稿如下，實作時以編譯結果為準：

```rust
pub trait Capability: Send + Sync {
    fn run(
        &self,
        work: &mut Work,
        cancel: &CancellationToken,
    ) -> impl Future<Output = Result<(), RunError>> + Send;
}

let agent = Loop::new(8, ToolCalling::new(tools, hook, Person::new(model)));
```

`run` 收一件工作和一個取消訊號（`CancellationToken`，外面可用它通知「請停止」）。最後一行由內往外讀：用模型建出人，包上工具呼叫，再包上迴圈；8 是回合上限（現有程式的預設值也是 8）。

為什麼這樣包：

1. **相依靠型別保證。** 批准用的 `hook` 是 `ToolCalling::new` 的參數，沒有工具呼叫就接不上批准；組裝錯了，編譯就過不了，不會在執行時默默失效。
2. **載入就是組裝。** 產品用的命令列程式（CLI）、比賽版（第五節）、只會一問一答的小幫手，只是載入的能力不同。
3. **人與能力可以分開。** 人所在的 crate 不依賴任何能力，能力的 crate 依賴人，方向只有一個。這條規則要寫成 `cargo xtask gate`（本專案的自動檢查命令）的檢查，不只靠文件。

放棄的做法：把能力放進 `Vec<Box<dyn Capability>>`（Rust 裝不同型別物件的清單，型別到執行時才確定），執行時才決定載哪些。放棄的是執行時彈性；換來的是上面第 1 點的編譯時檢查。現有程式也是這個分工：`Hook` 用泛型，只有要放進清單的 `Tool` 才用 `Box`（`crates/harness/src/tool.rs` 的 `ToolFuture`）。不同產品的組合，用不同的組裝函式表示，不用執行時開關。

## 三、優先級與排程：每個判斷用什麼算法

原則（使用者 2026-11-16 定）：優先級的判斷全部由程式與算法做，不由模型估；同樣的輸入一定得到同樣的順序。每個算法在實作前先寫在這裡，包含放棄的做法與代價。

### 輸入從哪來

- 任務由請求者建立，帶三個欄位：`urgent`（急，是或否）、`important`（重要，是或否）、`goal_id`（屬於哪個目標）。
- `important` 沒填時，用相等比較決定：任務的 `goal_id` 等於人目前的目標，就是重要，否則不重要。`urgent` 沒填就是否。
- 不讓模型估急與重要，因為模型每次估的值可能不同，順序就無法重現。
- 這個預設規則還沒經使用者確認，見第七節。

### 選下一件事的步驟

1. **過濾**：沒有授權、超過預算、不在這個人職責內的任務，直接拒收並回報原因，不進入比較。
2. **依賴**：任務依賴圖必須是 DAG；有循環就拒收並列出循環。只留下前置任務（必須先做完的任務）都已完成的任務。
3. **繼承**：每件任務的有效象限，取自己和所有（直接與間接）等它完成的任務中編號最小、也就是最先做的一個。象限是依「急不急、重不重要」分成的四類，編號見下表。
4. **排序**：依「類別（控制命令排在任務前）、有效象限、收件序號」做字典序比較，取第一個。
5. **執行**：這件做完才重選。執行中新來的任務只進收件匣，不搶占。取消除外。
6. **記錄**：每次選擇留一筆紀錄：選了誰、候選有哪些、各自的象限與有效象限、是哪一項決定了順序。有紀錄，事後才說得出為什麼是這個順序。

象限編號，數字小的先做：

| 編號 | 象限         |
| ---- | ------------ |
| 0    | 急且重要     |
| 1    | 重要不急     |
| 2    | 急不重要     |
| 3    | 不急也不重要 |

### 範例

A（重要不急，象限 1）要等 B（不重要也不急，象限 3）先完成；C 是急但不重要（象限 2）。一開始只有 B 與 C 可做，A 還在等 B。

- 不做繼承：B 是 3，C 是 2，C 先、B 次之；A 要等 B 做完才能做，等於被拖到最後。
- 做繼承：B 繼承 A 的象限，變成 1，比 C 的 2 先。B 做完後，A（1）又比 C（2）先，所以順序是 B、A、C。

### 算法選擇與取捨

表中的 O(…) 是教科書上的工作量結論，不是本案實測。本案任務數預期很小（個位數到數百），所以工作量不是主要考量，可預測與可測試才是。

| 判斷什麼                   | 用什麼算法                                                                                                                                                                                               | 放棄什麼                                                                                                                                                                         | 代價與理由                                                                                                                                                                                                                                    |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 控制命令與任務誰先         | 同一個收件匣、同一個比較函式，比較鍵第一項是類別（控制命令 0、任務 1）。第一版控制命令只有「取消」                                                                                                       | 兩個佇列（控制一個、任務一個）                                                                                                                                                   | 單一收件匣只有一套排序規則，控制命令與任務同時到達時，不必另訂誰先。代價：兩者混在一起，要靠類別欄位分開                                                                                                                                      |
| 任務能不能進排序           | 規則逐條檢查（每條規則是一個回答「過或不過」的判斷），第一條不過就拒收並回報原因                                                                                                                         | 讓模型判斷「這是不是我該做的事」                                                                                                                                                 | 結果可重現、可測試。代價：職責要寫成規則，寫不出規則的職責進不來                                                                                                                                                                              |
| 有沒有循環依賴             | 深度優先搜尋（沿一條路走到底再退回）加三色標記（未訪問、訪問中、已完成）：走到「訪問中」的任務，表示繞回了自己的祖先，沿走過的路徑退回去就是那個循環；用顯式堆疊（自己維護的待走清單），不用遞迴；O(V+E) | Kahn 拓撲排序（反覆取出沒有前置的任務排成一列）：只知道有循環，剩下的節點還含循環的下游，不能直接列出循環；Tarjan 強連通分量（找出彼此繞得回來的任務群）：找得出所有環但程式更多 | 需求是「拒收並列出循環」，三色標記剛好給出路徑。代價：要自己寫顯式堆疊，避免依賴鏈很長時遞迴用光呼叫堆疊                                                                                                                                      |
| 前置任務是否完成           | 逐一檢查前置任務的狀態，全部完成才算可做                                                                                                                                                                 | 預先算出完整拓撲順序                                                                                                                                                             | 每次只需要下一件，不需要整條順序；做完一件就重選，狀態一直在變，預算的順序會過期                                                                                                                                                              |
| 優先級繼承                 | 在 DAG 上從最後面的任務往前掃一次（後面的先算好）：每件任務的有效象限 = 自己與所有直接後繼（等它的任務）的有效象限中最小的編號；O(V+E)                                                                   | 優先級天花板協定（Sha 等，1990）：要事先知道每個資源會被哪些任務用，Agent 沒有這種資訊；完全不做繼承：會發生優先級反轉（火星探路者號 Mars Pathfinder 的任務出過這個問題）        | 繼承只在算的當下有效，前置任務完成後，下次重算就不再被抬高，不用存、不用還原。代價：每次選擇都重算一次；任務上萬時要改成只更新有變動部分的增量算法，現在不需要                                                                                |
| 繼承時怎麼合併兩個等待者   | 取象限編號最小者                                                                                                                                                                                         | 逐欄位 OR（有一個急就算急、有一個重要就算重要）                                                                                                                                  | OR 會製造沒有任何人真的有的「急且重要」：一個等待者重要不急、另一個急不重要，OR 後變成 0（急且重要）。取最小編號不會憑空升級                                                                                                                  |
| 排序鍵                     | 字典序：（類別、有效象限、收件序號），逐項比較                                                                                                                                                           | 加權分數；最早截止時間優先（EDF）；最短工作優先（SJF）；多層回饋佇列                                                                                                             | 加權分數的權重沒有依據，微小改動就翻轉順序，不好解釋。EDF 與 SJF 需要截止時間或執行時間，我們沒有資料，估的值又不可重現。多層回饋佇列是為了在不知道工作多長時輪流切分處理器時間，不是我們的情況。代價：字典序不能表達「稍重要但很急」這種折衷 |
| 從候選中取第一個           | 對可做的任務掃一次，取比較鍵最小者；O(n)，n 是可做的任務數                                                                                                                                               | 二元堆（BinaryHeap）                                                                                                                                                             | 繼承讓比較鍵每次都變，堆要重建，等於 O(n log n) 又更複雜；n 很小，掃一次最簡單                                                                                                                                                                |
| 平手                       | 收件序號：收件匣發的遞增整數，不用時間戳                                                                                                                                                                 | 時間戳；隨機                                                                                                                                                                     | 時間戳可能同毫秒、也可能時鐘回撥；隨機不可重現。序號保證同時到達也有確定順序                                                                                                                                                                  |
| 同一時間做幾件             | 演員模式：一個 tokio（Rust 的非同步執行環境）任務擁有人與收件匣，外面只拿代號（handle）寄請求（來源 Alice Ryhl）                                                                                         | 用 `Mutex` 包住人；執行緒池                                                                                                                                                      | `Mutex`（互斥鎖）誰搶到誰做，破壞優先序；鎖若在等待非同步結果（await）時還抓著，又容易卡死。執行緒池讓同一個人同時做兩件事，違反「同一工作區只有一個寫入者」。代價：所有請求都要經過收件匣，不能直接呼叫                                      |
| 取消                       | 兩條路：任務還在排隊，收件匣的取消命令把它移除；任務已在執行，用取消訊號 `CancellationToken`（harness 已有）                                                                                             | 把取消也排在收件匣後面                                                                                                                                                           | 執行中的任務不看收件匣，排在後面就收不到取消                                                                                                                                                                                                  |
| 要不要搶占                 | 不搶占：這件做完才重選                                                                                                                                                                                   | 搶占式                                                                                                                                                                           | 打斷執行中的工具，會留下做一半的副作用（對外界造成的改變，例如寫了一半的檔）。代價：高優先的新任務最多等當前這件做完；一件的上限是任務逾時（現在 120 秒，手動批准 900 秒，`crates/agent/src/task.rs:15`）                                     |
| 防飢餓                     | 第一版不做，列為已知缺口                                                                                                                                                                                 | 老化（等越久，優先級越高）                                                                                                                                                       | 單一使用者的 Agent 實際風險小，尚未遇到。加了老化會破壞純字典序的可預測性，等真的遇到再加並附比較實驗                                                                                                                                         |
| 成本效率、解鎖價值、後繼數 | 第一版不做                                                                                                                                                                                               | 把它們加進排序鍵                                                                                                                                                                 | 都要估計值，現在沒有資料。研究（Türkakın 等 2021，比較 17 種專案排程規則）發現表現最好的是依「最晚完成時間」排，不是依後繼數（見下節）；但那是有資源限制的專案排程，適不適用 Agent 沒驗證。每加一項要先有比較實驗                             |

### 關於「分叉」

分叉指做完 A 之後，有幾件事可以接著做，也就是後繼數。做完 A 只有 B 可做時，後繼數是 1，這是允許的。「0 分叉」（沒有多出來的分支）與「出度 1」（圖論用語，從 A 往外連出 1 條箭頭）是同一件事的兩種數法，本文統一用後繼數。第一版不拿它排序。

### 資料與檔案

- 型別各一檔：`Request`、`Task`、`Priority`（急、重要兩個是否值，附算出象限編號的 `quadrant()`）、`Inbox`（收件匣，負責發遞增序號）、`Decision`（一次選擇的紀錄）。
- 函式各一檔：`select_next`（選下一件）、`ready_tasks`（找出前置都完成的任務）、`propagate_priority`（繼承）、`find_cycle`（找循環）、`passes_filters`（過濾）。
- 檔案放在 `scheduler` 的 `src/`，檔名同型別或函式名。

### 第一版不做

- 步驟邊界重排、暫停、繼續、重試。
- 跨 Agent 的請求：多個目標就開多個 Agent，各自有收件匣；別的 Agent 送來的訊息，當成一般請求。

## 四、harness 功能取捨

動手寫核心之前，先決定各家 harness（管模型、工具、授權與接續的 Agent 外殼）的功能「我們要不要、放哪裡」。目標是集各家優點、去掉缺點、保持輕量。證據來源是 `harness-study` 的 Claude Agent SDK、Codex、Gemini CLI、Google ADK、DeerFlow、Microsoft Agent Framework（下稱 MAF）六份模組版 PDF，與 topics 七份比較；各家文件寫「文件未載」的地方，本表也是未查證。

名詞：場次（session）是一段對話的完整紀錄，可存檔、接著跑、重建。回呼（callback）是核心在特定時間點呼叫外部程式；我們只留 `Hook` 一種。MCP 是讓外部程式提供工具給 Agent 的標準協定，它是「工具的來源」，不是回呼。

輕量的量化界線（本專案自訂的判斷，不是來源數字；階段 1 結束時用實測行數檢討）：

- 核心 crate `harness` 不碰檔案、網路、資料庫；只依賴非同步與取消的基本套件。
- 核心程式碼不超過 1,500 行（2026-10-28 現況 296 行）。超過就把功能拆成獨立 crate。`capabilities` 與 `scheduler` 先套用同一條線。
- 核心對外匯出不超過 20 個名稱。能檢查對外介面大小的工具（如 `cargo public-api`、`cargo semver-checks`）是否可用於本專案，未查證。

放哪裡的三種答案：**核心**（在 `harness`）、**能力**（在 `capabilities` 或 `scheduler`，或之後各自的 crate）、**擴充**（有需要才做的獨立 crate）。

要避開的反例：

- 同時有多套迴圈（Gemini 四套），行為會分歧：只有一個迴圈能力。
- 停止靠丟例外，各處理流程接住例外的方式不同（MAF）：停止原因用列舉，不用例外。
- 模型回空內容時重試，沒有次數上限（Gemini）：所有重試都要有上限。
- 只用除錯用的斷言（只在開發時檢查）保證「同時只有一個回合」（Codex）：要用正式檢查並有測試。
- 只寫入、不強制落盤（三家都沒有 fsync，即要求作業系統把資料真正寫進磁碟）：場次寫入要定義落盤時機並測試崩潰。

做的順序：

- 階段 1 先做：壞工具參數回報模型（現在會中止整個任務）、呼叫與結果配對鐵則、停止原因列舉（成功結束也要有原因）。
- 場次介面與一致性測試排在階段 1 之後、接上真正的 Gateway 之前，因為續跑與取消接續都依賴它。
- 現況（2026-10-28 讀程式）：`Agent::run` 吃一句提示、回傳訊息與文字；停止只靠 `RunError` 四種；沒有場次、沒有成功端的停止原因、沒有 MCP。
- 六份模組版文件多處標「文件未載」：Gemini 場次儲存細節、ADK 與 MAF 的匯出清單、DeerFlow 停止條件，未回原始碼核對。

## 五、比賽版（PLE）：候選用途，尚未決定參加

PLE 是 Google 與 Mercor 的工程題自動做題比賽。官網 ple-bench.com（2026-11-17 讀）列的比賽期間是 2026-11-09 至 2027-01-05，前三名獎金 25 萬、10 萬、5 萬美元，每組「執行框架（即 harness）加模型」在不公開的隱藏題上跑 3 次。

評分分兩種。以限制與設計目標評分的題，每個交付項的分數是 `s = 0.4p + 0.6·G·O'`（p、G、O' 各代表什麼，本文未查證），硬性限制破任何一條，該項最高只剩 0.4 分。其他題由 LLM（大型語言模型）評審對照評分標準打分。兩者都出自官方 `docs/rules.md`。

mortal agent 能自由載入或不載入能力，正好符合比賽要拆掉部件做對照實驗的需求。本節是評估，目前沒有比賽版程式，沒有跑過任何比賽題，沒有花費。

- 現有 Agent 不能直接拿去比賽：比賽全自動、每題一個全新容器（隔離的執行環境）、最長 6 小時，沒有人批准、沒有桌面畫面，要接比賽方規定的 WebSocket（網路上的雙向即時連線）協定。
- 比賽版的組合：人加迴圈加工具呼叫加「檢查員」（交件前逐條對照題目要求）；不載批准與排程，因為全自動、一次一題。
- 新增的部件：協定層（`exec`、`read_file`、`write_file`、`http` 四種請求）、檢查員、先交件、時間預算。保留任務迴圈與模型連線；批准、任務庫、桌面、知識庫不用。
- 比賽程式放獨立 GitHub repo；需要的兩個 crate 用複製的方式帶過去，因為比賽建置時是不帶帳號的匿名複製，拉不到私有 repo 的子模組（git submodule，repo 內嵌的另一個 repo）。
- 消融實驗（一次只換掉一個部件，其餘不動，看分數掉多少）每一組對應一個組裝函式：A0 全載、A1 無檢查員、A1n 檢查員照跑但一律放行（負向對照：檢查員形式上還在，但失去作用）、A2 無先交件、A3 無時間意識、A4 規劃執行檢查三角色、A5 預算三檔、A6 結尾不附證據、A7 換模型。
- 公平競賽規則（不寫死答案、不讀評分程式、只連模型主機、不外傳題目內容、模型名從環境變數讀）各要配一項自動檢查（目前尚未實作）；規則原文在 google-research/ple 的 `docs/rules.md` 與 `kit/README.md`。

事實來源：google-research/ple 的 README 與 docs（rules、protocol、models、artifacts）、`kit/README.md`、`eval/README.md`、`eval/dev_set.yaml`，以及 Mercor 2026-11-03 的部落格。

還沒查證：

- 有沒有書面報告：官網與官方 repo 都沒提；先前記的配分（25／25／15／20／15）只來自使用者貼文，Kaggle 頁面讀不到，視為未證實。
- 程式可讀性是否計分，找不到原文；官網只寫效能計分。
- 隱藏題的排名方式、成本是否計分，官方 repo 寫「之後公布」；提交截止的確切時點，官網只列比賽期間，未單獨標示。
- Rust 能否在比賽的建置環境編譯：官方建置映像（debian:bookworm，預先做好的系統環境）附編譯器，`install` 步驟可上網，最長 30 分鐘；但文件沒寫有 Rust 工具鏈，需在 `install` 裝，並用官方 kit 實測。現有模型連線能否接比賽的模型代理，也還沒試。
- 一次完整開發集實跑的時間與費用還沒量；跑開發集要花模型費用，需要使用者同意後才跑。
