## 原始審查文字

**審查依據：** 只讀你貼的兩份文件，沒有執行工具，也沒有驗證任何外部來源。以下判斷屬 AI 推論，未實測。

**高**

1. **授權與取消的空窗。** 文件寫「執行前再次核對」，但核對、領用授權、啟動工具是三步，取消可插在中間。
   - 修法：「領用授權＋標記工具已啟動」放進同一個 `BEGIN IMMEDIATE` 交易，條件含狀態、世代、未取消。
   - 還要規定每條連線都設 `synchronous=FULL` 與 `busy_timeout`，不能只靠文件宣告。
2. **「先核對舊執行者已停止」沒有機制。** SQLite 判斷不出舊程序死了沒有。
   - 需補：租約加心跳、工作資料夾的 `flock`、行程群組或 cgroup 終止，才能處理孫程序和 PID 重用。
   - 「取消後 10 秒無寫入」不能證明零寫入，延遲工具可能第 11 秒才寫。要改成確認整個行程群組已終止。
3. **全機索引的權限預設太寬。** 預設納入文件、下載、桌面，卻只寫「敏感憑證不向量化」，沒有偵測規則，例如 `.ssh`、`.env`、瀏覽器設定檔、密碼庫、`.git` 歷史。
   - 檢索也會繞過「敏感工具預設拒絕」：Agent 不必讀檔，就能從索引看到內容。
   - 索引庫本身成為彙整全機內容的高價值目標，而且文件內容進模型後有提示注入風險。
   - 修法：改成預設不納入、使用者逐一選入；檢索結果要走與讀檔相同的授權。

**中** 4. **資源效率。** Rust、Python（Docling、LlamaIndex）、PostgreSQL 三層常駐，對桌面工作站成本高。

- LlamaIndex 只用快取與去重，但版本發布和雜湊又自己做，復用價值存疑。
- 第一階段可先用 SQLite FTS5 或 tantivy 做全文，向量後補。
- multilingual-e5-small 在 CPU 上對 10 萬檔的吞吐沒估算。

5. **兩個資料庫的一致性。** 任務在 SQLite、知識在 PostgreSQL，「回答前再確認權限與版本」要跨兩庫。授權和 Memory 存哪邊也沒寫。
