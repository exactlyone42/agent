## 從安裝到使用：使用者實際會經過什麼

以下是產品應提供的流程，不是現在已可下載或執行的安裝指令。正式套件名稱、下載網址、已測 OS 清單與模型大小必須隨正式版本發布，不能虛構。

| 步驟              | 使用者做什麼                                                                          | 程式必須完成什麼／如何驗收                                                                                                                                   |
| ----------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. 取得安裝包     | Linux 使用者下載原生 CLI 套件；桌面使用者下載桌面安裝包；管理者可用同版離線部署包     | CLI 發布原生壓縮包及受測發行版的 .deb；桌面以 .deb／AppImage 為首輪候選，隨包列支援系統及依賴。校驗簽章、雜湊與平台，損壞或不相容即拒絕；不是只有 Git 原始碼 |
| 2. 安裝與環境檢查 | 原生 CLI 可裝使用者目錄；系統套件由管理者安裝；桌面以系統套件工具或啟動 AppImage 使用 | 安裝器檢查磁碟、權限、容器環境及模型資產；不要求手工編譯、建 DB 或安裝 Python。缺容器時說清楚缺項與修復方式；管理權限不偷偷取得                              |
| 3. 初次設定       | 設定模型入口、核對可讀資料及排除規則、資料外送政策、資源與索引空間上限                | 安全保存秘密，顯示實際來源範圍及將下載資產的大小／授權；離線包從本機匯入。自動準備資料表與固定版本容器，常駐服務只綁本機                                     |
| 4. 啟動工作       | CLI 在工作資料夾輸入任務；桌面選工作區並建立任務                                      | 立即接受任務，背景開始發現與索引；來源未處理時可受限直接讀檔，不假稱全機已查完。索引狀態與任務狀態分開                                                       |
| 5. 授權與驗收     | 看動作範圍與差異，批准或拒絕；必要時取消、重開接續                                    | 未授權不動作；完成後讀回檔案或畫面。未知結果顯示待處理，不因模型說成功就通過                                                                                 |
| 6. 維運與更新     | 看診斷、知識更新落後時間、備份、版本與更新通知                                        | 同一安裝管道負責更新；更新前檢查任務、備份與資料版本。失敗能保留舊程式，資料回退須使用驗證過的備份與遷移；移除程式不自動刪除資料                             |

正式安裝包必須提供可重跑的非互動安裝設定給 IT 部署，秘密不得放命令列。離線部署包須包含獲准再散布的模型／容器與版本清單；不能再散布的依賴明列取得方式，缺件就不得標完整就緒。預檢通過後的完整安裝不要求使用者拼湊多個開發工具；安裝失敗不能留下假正常服務。

npm 包裝只負責啟動相同原生核心，與原生版測參數、訊號、退出碼及版本一致；它不是容器或模型已安裝的證明。完整知識服務未就緒時，基本任務可繼續使用，但產品明列「知識功能未就緒」，不得通過完整安裝驗收。

容器路徑固定為 **Docker Engine rootless**；第一個受測 OS 為 Ubuntu 24.04 LTS x64。IT 先安裝 uidmap、設定 subordinate UID/GID 與使用者服務前置；這一步可能需要管理權限。前置具備後，應用安裝器用一般使用者建立 rootless 容器環境及服務。只有 CLI 執行檔的使用者目錄安裝不需管理員，不把它等同完整整機知識安裝。[Docker 官方前置](https://docs.docker.com/engine/security/rootless/)

Docling、LlamaIndex、Python、OCR／向量依賴都在固定版本容器；主機不裝 Python 套件。兩專案的程式授權與每個模型／相依套件的再散布權須在 P01 清單逐項核對；專案採寬鬆授權不保證模型均可離線再散布。P03a 即建立發布簽章與驗章測試，正式 Linux 包必須附可信公鑰可驗證的簽章；SHA-256 不能代替簽章。桌面更新另遵守 [Tauri 簽章驗證](https://tauri.app/plugin/updater/)。

## CLI 與桌面分別長什麼樣、如何交接

| 能力           | CLI 使用方式（命令契約待實作）                                     | 桌面使用方式                                                 |
| -------------- | ------------------------------------------------------------------ | ------------------------------------------------------------ |
| 交代任務       | `agent-platform` 進互動工作區；輸入目標，顯示任務識別、動作與進度  | 左側工作區與任務清單；中央任務內容及進度                     |
| 看授權與成果   | 終端顯示動作、讀寫範圍、差異、允許／拒絕；完成附證據位置           | 待授權區、差異檢視、成果與驗收頁；高風險操作不藏在聊天文字裡 |
| 停止與接續     | Ctrl+C 取消；`resume <id>`、`status <id>` 讀回任務                 | 停止、接續與狀態按鈕；操作同一任務，禁止兩個入口同時執行     |
| 搜尋與知識維護 | 提供查詢、範圍、索引進度、暫停／繼續／停用入口                     | 知識來源、處理進度、排除與失敗清單、引用及最後查證時間       |
| 自動化與診斷   | `run --json` 結構化事件、`doctor` 診斷；另提供備份／還原與管理入口 | 設定、診斷與備份還原畫面；同用後端能力                       |

桌面不解析 CLI 螢幕文字，不另做第二套 Agent。關閉視窗時清楚說明任務是停止、等待還是繼續在已啟用容器 worker 中執行；沒有背景能力就不能假稱持續工作。桌面包帶相容核心，不能默默挑 PATH 中另一版。可替換編輯器不等於現在就要重造 IDE。

## 產品形態與取捨

| 方向               | 使用者主要做什麼                           | 優點與代價                                          | 建議                   |
| ------------------ | ------------------------------------------ | --------------------------------------------------- | ---------------------- |
| 可安裝 CLI         | 在工作資料夾交代任務、批准差異、停止及接續 | 最快驗證執行能力；終端操作有學習成本                | 先完成的操作入口       |
| 桌面 ADE           | 看多個任務、處理授權、核對成果與整合修改   | 直接改善 Agent 工作流程；仍需終端與工作區管理       | CLI 穩定後的主要方向   |
| 完整 IDE           | 大量手動編輯、跳轉定義、除錯、管理擴充套件 | 一站完成開發；編輯器與擴充生態維護量很大            | 有實際需求再升級       |
| 修改 Orca 作為產品 | 沿用現成工作台，加入本案任務驗證           | 工作台功能現成；須持續跟進上游，與原 Tauri 選型不同 | 保留比較，不在本輪改選 |

Orca 的官方來源目前採 MIT，程式設定顯示 Electron。這讓「修改 Orca」成為可研究的選項，但不代表其依賴、品牌及服務均可無條件重用。[O4](https://github.com/stablyai/orca/blob/main/package.json)[O5](https://github.com/stablyai/orca/blob/main/LICENSE) 本輪維持既有 Rust／Tauri 方向；先把自己的 CLI 放進現有 Orca 使用，便能測試 ADE 需求，不必立即重造工作台。

進入桌面前，先在自己的 CLI＋既有 Orca 完成五個有實際檔案成果的任務，記錄切換介面、找授權、看差異與重啟恢復的阻礙。若主要問題是任務協調，做 ADE；若至少三個任務反覆需要完整程式導航、除錯或既有擴充套件，先比較整合既有 IDE 與另做 IDE 的成本。這是規劃的決策門檻，不是已取得的使用數據。

## 核心與介面如何共用

[開啟直線版架構與分步驗收圖（PDF，4 頁）](docs/research/cli-first-20261025/architecture-straight.pdf) · [瀏覽圖形版（HTML）](docs/research/cli-first-20261025/architecture-straight.html)

圖形以獨立排版交付，不用 Markdown／Mermaid 原始碼代替成品。第 1 頁為架構，第 2 頁為執行流程，第 3–4 頁為工作順序與驗收。

圖為建議設計，不是目前已存在的系統。CLI 直接呼叫共用 Rust 核心；桌面以隨應用啟停的子程序，透過結構化訊息取得事件、送出授權及取消。桌面不解析終端畫面的文字來判斷成功，也不另做第二套 Agent 迴圈。此子程序不是常駐背景服務；無介面仍持續執行的工作，留到容器 worker 階段。

Gateway 維持獨立模型 API，任務狀態與寫檔授權留在 Agent Platform。第三方 Agent 的既有訂閱登入不等於可透過 Gateway 任意轉用；將來若整合外部 CLI，使用其支援的程序介面與原有認證，不匯出它們的秘密。

為避免第一次使用就要求架資料庫，建議 CLI 任務狀態改用本機 SQLite；知識庫、多人服務與向量檢索再按原計畫使用 PostgreSQL。這是目前選定的單機設計，尚未完成實作驗證或搬移資料。只做一個本機狀態實作，不先建雙資料庫抽象；P01 要以交易、中斷恢復與兩個程序搶同任務的測試決定是否符合發布門檻；不通過就修訂選型與相依契約。

前景任務先維持一個工作資料夾一個寫入者。狀態資料與使用者原始檔分開；憑證不可出現在命令列參數、一般日誌或成果報告。未驗證成功只能顯示等待、失敗或結果未明，不能因模型宣告完成就成功。

| Tool calling（模型要求呼叫工具） | 驗參數、核對授權、執行、記錄結果、獨立驗證；MCP 工具接入沿用 rmcp 候選       | P02           |
| 任務保存                         | 任務、步驟、工具意圖與回執、授權、取消請求、成果證據                         | P01、P04      |

### SQLite 適不適合

建議單機 CLI／Tauri 用 SQLite 保存任務；同機一個任務擁有者控制執行。知識索引仍用本機 PostgreSQL／pgvector，資料庫不共用任務真相。SQLite 的優點是免架伺服器、交易完整、可隨程式交付；不是因為資料小才用，也不代表它能替我們執行或停止工作。

別人的做法：Codex 的 state 模組使用 SQLite，本輪讀到實際連線設定及狀態、佇列等資料庫路徑；其 rollout 資料與 SQLite 並存，不能說全部執行都只靠 SQLite。[Codex 原始碼](https://github.com/openai/codex/blob/main/codex-rs/state/src/sqlite.rs)。LangGraph 把流程快照與跨任務記憶分開；官方把 SQLite 列為本機開發保存方式，PostgresSaver 用於持久服務，不能把 SQLite 套件存在說成大型服務推薦。[LangGraph 保存設計](https://docs.langchain.com/oss/python/langgraph/persistence)

| 動作 | SQLite 保存什麼                                    | 執行核心必須做什麼                                             |
| ---- | -------------------------------------------------- | -------------------------------------------------------------- |
| 執行 | 領取者、嘗試次數、工具意圖、回執、驗證結果         | 短交易搶任務；模型與工具執行時不持有資料庫交易                 |
| 授權 | 誰批准哪個工具、參數摘要、範圍、有效期限與使用狀態 | 執行前再次核對；參數或範圍改變就重新判斷，不能沿用籠統批准     |
| 取消 | 先存取消請求，之後存已停止或結果未明               | 禁止新工具、停止子程序並核對；遠端操作可能已生效，不能假稱回滾 |
| 接續 | 已完成步驟、未完成意圖與外部操作識別               | 先核對舊執行者已停止；未知副作用查外部回執，不能直接再做一次   |

本案採單一任務資料庫、WAL（讓讀取與寫入較少互相阻塞）與短交易；同時仍只有一個寫入交易。重要授權及執行意圖以 FULL 同步設定驗收，鎖等待與重試有上限；資料庫只放本機磁碟，不放 NFS 或同步雲端資料夾。備份用 SQLite 備份介面，不只複製仍在寫入的主檔。[官方適用範圍](https://sqlite.org/whentouse.html)、[WAL 限制](https://sqlite.org/wal.html)

取消與領取必須在同一資料庫條件更新，避免取消後又派發。接續使用執行世代識別，舊執行者的回報不可覆蓋新狀態；這個識別本身不能阻止外部工具繼續寫，仍須實際停止舊程序。無法確認停止時維持「結果未明」，禁止重啟有副作用步驟。資料庫交易無法和任意外部 API 形成一次性交易；優先使用工具支援的冪等識別（重送也不重複執行），否則查證或人工處理。

補充取消契約：領用一次性授權與寫入工具「準備執行」意圖，必須在同一短寫入交易檢查任務世代及取消狀態；意圖不等於工具已啟動。單一執行者將派發與取消處理串行化，啟動後另存回執，崩潰空窗標為結果未明。每條寫入連線設定 FULL 與有限鎖等待。工作區用作業系統鎖確保唯一寫入者；執行者以程序身分、心跳與所屬程序群組追查，心跳超時不等於已死亡。確認可控程序樹已停止、待派工作已撤銷，才回報本機取消完成；10 秒觀察只是額外故障測試，不能代替終止證據。遠端工具另查狀態，無法確認就不宣稱已停止。

採 Codex 時優先沿用它的執行與保存介面；平台只保存平台授權、任務映射與獨立驗收，不複製另一份核心執行進度。所有工具入口必須受平台政策約束，不能攔住的核心不能通過 P01。採 Rig 時則由平台保存主流程。P01 同題驗證這個邊界，禁止兩套迴圈同時控制任務。Computer Use 也走同一意圖與回執契約，帶觀察序號、時間及視窗身分；P07 再依實測增加欄位，不預造未使用的資料表。

授權真相保存在任務 SQLite；文件有效版本與來源權限資料在知識庫，查詢由核心先驗範圍，再由知識服務核對來源；送模型前再次驗授權世代及來源版本，不聲稱跨兩庫交易。Memory 的同意、候選與有效內容映射採 SQLite 初版提案，內容可指向受限產物；詳見 agent-method.md 的修訂契約，仍待 P06 驗收。資料庫不可用或權限狀態無法核對時拒絕提供片段。

P01／P04 要測兩程序搶同任務、授權與取消競爭、工具前後崩潰、磁碟滿、鎖超時、資料升級及備份恢復；先不宣稱效能或可靠接續已通過。若未來跨機 worker 要共享任務，或量測顯示寫入等待破壞互動目標，再採伺服器任務庫；不讓遠端程序直接開 SQLite 檔。

## RAG、流程編排與 Rust 套件選擇

RAG（先查自己的資料，再根據查到的內容回答）是正式交付範圍，不因 CLI 先行而取消。前版把它併在 P05–P07 一列，漏寫套件與驗收細節；本節補齊。P03 是檔案任務的早期可用版，P05 必須在 CLI 階段完成知識問答，不必等桌面；只有 P03 通過不能稱完整 Agent Platform 已完成。

| --------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| LangGraph | 管理有分支、等待授權、保存狀態及恢復的執行流程      | 本輪確認官方 Python、JavaScript 文件；未確認官方 Rust 發行版。社群 `rust-langgraph` 明列非官方；另一個 `langgraph-rs` 是把 Python 流程轉成 Rust 的工具，兩者不能混稱。[官方 Python](https://docs.langchain.com/oss/python/langgraph/overview)、[官方 JavaScript](https://docs.langchain.com/oss/javascript/langgraph/overview)、[社群執行框架](https://github.com/kareem2002-k/rust-langgraph)、[轉換工具](https://github.com/genai-rs/langgraph-rs) |
| LangSmith | 追查每一步發生什麼，並評測回答及 Agent 表現         | 本計畫列入的是 LangSmith；不將未確認的拼寫另當一套產品。官方支援 OpenTelemetry，也就是通用的執行追蹤格式；Rust 可評估透過此格式串接，不必為追蹤改用 LangChain。[官方追蹤介面](https://docs.langchain.com/langsmith/trace-with-opentelemetry)                                                                                                                                                                                                         |
| Rig       | Rust 原生的模型與 Agent 組件                        | 是本 repo 已登記的核心候選，不是 LangChain 的 Rust 官方版；先驗既有固定版本，不追著 main 換版。[專案來源](https://github.com/0xPlaygrounds/rig)                                                                                                                                                                                                                                                                                                      |

所以「有 Rust 可用」成立於**已有 Rust 專案與候選組件**，不等於「LangChain／LangGraph／LangSmith 三者都有官方、完整、已驗證的 Rust 等價版」。這些不是每個都必裝的套件組合；RAG 也不依賴一定要用 LangChain。

### 本案採用順序

1. **P01 選執行核心**：延續 Codex 與 Rig 的同題比較，不另開第三套主迴圈。本機 `Cargo.toml` 已將 `rig-agent`、`rig-core` 固定在 `55cd481a2421fd5da468b5bd6afc6ac876883599`；這只證明依賴已登記，本輪未重新編譯或驗證 RAG。
2. **P02／P04 驗流程能力**：先測選定核心的授權、取消、保存與接續。只有具體缺口需要分支流程時，才試接社群 Rust 圖式框架；用相同崩潰、重播與副作用案例比較。名稱含 LangGraph 不保證恢復安全。
3. **P05 選資料處理組件**：以整機知識庫方案的 Docling＋LlamaIndex 作首次試接；Rust 負責控制，不自造文件解析器。Swiftide／langchain-rust 用同題比較後再決定是否替代。採用前鎖定版本、授權與依賴。
4. **P02 起留下可追查事件，P08 完成評測**：沿用 Rust tracing／OpenTelemetry 與本機獨立驗證器；LangSmith 是可選查看與評測平台，不是任務成功的裁判。未獲資料外送與服務費用授權，不把文件、提示或工具內容送到外部平台。

這是選型優先序，尚未完成 Swiftide、langchain-rust 或 Rust 圖式框架的建置、維護狀況與相容性驗收；不宣稱它們可以直接替換既有核心。候選先以固定資料測試，不以星數、套件名稱或 README 宣傳判定成熟度。

### P05 的實際交付與驗收

依最新需求，以[整機知識庫方案](docs/research/cli-first-20261025/knowledge-plan.md)為準：安裝後背景發現檔案，按用途解析、結構切片、向量化，持續偵測異動。優先試接 Docling＋LlamaIndex；Swiftide 與 langchain-rust 保留替代比較。P05a 的常用格式與增量更新是完整安裝版前置；OCR、大檔及專業格式在 P05b 逐項驗收。原 60 題檢索驗收、權限、引用及資料不足不亂答的要求保留。

## 安裝、更新與平台

1. 先交付 Linux x64 的固定版本壓縮包，包含原生程式、授權清單與 SHA-256 校驗碼；從乾淨測試帳號安裝到使用者目錄，不需管理員權限。校驗碼須從可信發布來源取得，不能把同站校驗當成完整簽章保證。
2. npm 是第二個入口：只選對應平台的同版程式，傳遞參數、輸入輸出、取消訊號與退出碼。先以本機打包安裝驗證，不先公開發布套件，也不虛構尚未註冊的 npm 名稱。
3. 更新由安裝管道管理，避免 npm、內建更新與桌面安裝器互相覆寫。初版先採手動更新；不在任務執行中更換程式。測試中斷下載、舊版仍可啟動與合成資料升級；不相容的資料版本明確拒絕，不假稱直接降版就能復原。
4. 桌面包內附相容核心，不要求使用者先裝 npm。版本與介面不相容時明確擋下，不悄悄改用 PATH 中另一版程式。
5. Linux arm64、macOS、Windows 依真實測試資源逐一加入；僅能交叉編譯不等於實機通過。Linux 發布簽章是必要門檻，使用自管金鑰不需採購商業憑證；商店／其他平台付費憑證及外部發布另依授權處理。移除程式不自動刪除任務資料與使用者檔案。

## 先定三種驗收責任

| 負責者               | 必須做什麼                                                                         | 不能代替什麼                                                     |
| -------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 程式測試與獨立驗證器 | 核對檔案、資料庫、程序、權限、引用版本、退出狀態；留下可重跑命令及實際輸出         | 無法單靠測試判斷使用者是否看懂、內容是否符合專業需求             |
| AI 審查者            | 讀需求、差異、測試與原文，提出反例；對語意內容按固定標準盲評，指出理由與來源       | 不因作者或審查模型說「成功」就放行；不裁定自己的工具是否真的執行 |
| 真人驗收者           | 在真實入口操作，確認結果有用、授權可理解、能停止及接手；專業文件由熟悉內容的人確認 | 不要求真人代跑每次單元測試，也不能用主觀滿意覆蓋安全失敗         |

AI 可協助產生測試，但測試的預期結果必須來自需求、人工標註或獨立資料，不由待測模型自己決定。審查與生成分開執行；同一模型換角色不代表真正獨立。使用 Claude Code 做設計與重要實作審查，保存模型版本、輸入、原始回應、每條意見的處理與證據；審查器不可用時標「未審」，不偽稱通過。

真人驗收放在每個可用里程碑，其他工作可在依賴允許下繼續。尚未真人驗收顯示「程式檢查通過，待真人驗收」，不得標成產品完成。高風險權限、資料外送或費用仍以既有授權為準，不把驗收同意當成擴大授權。

## 每張工作卡共同要交的東西

先寫需求編號、前置步驟、允許改動範圍、輸入資料、預期成果、驗收案例及停止條件，再派 AI 實作。每張卡明列一位具名真人驗收負責人及其角色；步驟 3 需要未參與開發者，步驟 7 需要熟悉該格式內容者，同一人符合條件可兼任。尚未找到人就標「待真人驗收」，AI 不得代簽。一次卡片交付一條可操作流程；依賴不確定先做隔離試接，不一次造完整框架。

交付包包含版本與依賴、實際成果或差異、測試命令與輸出、反例、AI 審查及處理、真人操作紀錄、未驗範圍、回退／接續方法。證據與秘密分開，日誌不放完整文件、憑證或個資。所有證據對應同版程式與同版測試資料；修正後重跑受影響項目，公開交付前再過專案全套檢查。

## P05 詳細工作：三塊 RAG 如何做完

以下 R01–R15 是 P05 的子工作，沿用同一執行任務，不是另開一份計畫。每步都要交付可讀回的資料、固定版本設定、正常與錯誤案例及原始測試輸出。工程基準先建立，不代表功能可以只做到基準就交付；所有承諾格式、三塊功能及品質驗收都要完成。

### R01：固定資料、權限及品質基準

- 輸入：人工／合成文件，涵蓋中文、表格、數字與否定詞、跨文件問題、無答案、矛盾版本；目標機器規格及來源授權。
- 程式：建立版本清單與內容雜湊；區分調整資料與未拿來調整的測試題；準備 100,000 檔案及真有內容的 1 GiB 大檔容量案例，不拿空洞檔算吞吐。
- AI：協助提出問題與反例；真人核對原文、標準答案與不可答案例。搜尋用的虛擬問題與評測題分離，禁止測試題流入索引增強。
- 交付／驗收：至少 60 題及正確原文位置；開發前固定指標與門檻。先以至少 12 題校準 AI／真人判分、報分歧；這只供初始校準，不是企業容量或穩定品質的證明。正式版另以真實代表性資料、重複測量及各類型結果驗收。

### R02：安裝時發現整機資料，但不阻塞工作

- 程式：先取得來源範圍同意；用 walkdir 分批列目錄與檔案資訊、notify 收異動。只先讀路徑、大小、時間與檔頭；不為盤點每個大檔先讀完全檔。保存游標，先啟監看再掃描並核對期間變更。
- 排程：點名文件與當前任務優先；常用文件與大型知識文件各有名額；等待過久提高優先。暫存、編譯輸出、索引自身與敏感秘密排除；大檔不得永久跳過，無法解析需明列。
- AI：僅在用途不清且值得處理時協助分類，不讓模型決定擴張讀取權限。
- 交付／驗收：來源清冊、排除原因、待處理數與大小；符號連結迴圈、無權目錄、離線磁碟、重複內容各測一次。重啟從游標續跑；任務在盤點未完時可接受與執行。

### R03：按格式解析為可追溯結構

- 程式：Docling 作一般文件候選，Tree-sitter 作 TS／RS 結構；郵件先抽主旨、時間、內文及關聯，附件作獨立子文件。解析程序隔離、不連網、不執行巨集。每個組件先固定版本、授權與記憶體實測。
- 格式：PDF／DOCX／MD／HTML 保留段落、章節與頁碼；XLSX／CSV 保留工作表、欄名、儲存格與顯示值；EML／MSG 保留附件關係；掃描 PDF／圖檔另走 OCR；設計檔按 DXF／DWG／PSD／FIG／STEP 等逐種選專用工具，不能把預覽縮圖當已理解原檔。
- AI：可協助辨字與圖面理解，但產物標記模型與信心／未確認範圍；結構化文字和原文位置保留，不用摘要取代原文。
- 交付／驗收：每格式可讀、損壞、加密、不支援樣本；對照原頁、儲存格或函式行號核對順序、數字、單位、表格、附件。超時與超記憶體可終止並留原因；各格式「可抽文字／可辨字／理解結構」分級，不一律宣稱支援。

### R04：結構、語意與 AI 選切點

- 程式：先按章節、段落、表格、函式及模型長度限制切片；保存來源版本、原文範圍、父章節與鄰接關係。跨頁表頭、單位與例外條款不可遺失。
- AI：語意向量法比較句群差異；語言模型法只回傳段落識別的分組與切點，不重寫原文。優先處理結構不清、熱門或已出現檢索失敗的文件，避免初次全機等待每段模型分析。
- 程式核對：識別存在、原順序、內容完整覆蓋、長度與表格邊界；不合法回退結構切片，保留失敗原因。
- 交付／驗收：三種切法同題比較找回率、完整性、時間與模型用量；以漏段、錯序、截斷表頭反例證明檢查器會擋。沒有證據改善者不設為預設；仍完成實驗與決策報告。

### R05：虛擬提問、背景與多種搜尋表示

- AI：每片最多 3 個可由原文回答的問題，附支持位置；可生成簡短文件背景。無法由原文支持的問句拒收，生成文字不得升為事實。
- 程式：同題比較 A 原文向量、B 原文附問後向量、C 原文與各問獨立向量；保存表示種類、來源片段、模型、提示及版本。C 命中先映射回原文再去重與排序，不以問句數加分。
- 交付／驗收：原文映射、生成用量與同題結果；刻意加入錯誤問題、未支持數字、撤權來源測拒收／失效。保留測試題和同義改寫不得回灌增強。程序維持已知可用基準，生成失敗不能阻擋全庫。

### R06：向量化、去重與版本發布

- 模型：先試 multilingual-e5-small，固定 tokenizer、維度、query／passage 前綴與正規化設定。片段與問句表示分開記錄，不混用不同向量空間。
- 程式：有界批次、內容與設定快取鍵、失敗續跑；來源解析前後核對版本。新版本所有必要內容就緒後以交易發布，半套結果不可見。相同內容可省計算，但路徑及來源權限不能合併。
- 比對：E5 正規化向量先採內積；單位向量下與 cosine 排序等價，平方 L2 為 2−2×內積。向量長度不是原文長度，也不是通用品質分數；未正規化模型依官方訓練契約選度量，不任意套同一方法。
- 交付／驗收：相同文件再次執行零新增向量計算；改段只重算受影響內容及相鄰切點；換模型／切片規格正確失效。NaN、零向量、錯維度、批次中斷與混版本必須拒絕或續跑，不發布假完整。

### R07：關鍵字與向量共同找證據

- 程式：先按任務與來源權限過濾有效版本，再分別查全文與向量；按排名融合、映射原文去重，不直接加未校準分數。中文斷詞、型號、數值、否定詞另驗；PostgreSQL 原生全文不冒稱 BM25。
- 加速：先以精確向量搜尋建立正確性對照，再試 pgvector HNSW；近似索引參數、資料量、權限過濾選擇性與更新狀態一起記錄。不足候選時有界擴大或退回精確查詢，不能漏權限過濾。
- 交付／驗收：純關鍵字、純向量、混合比較 Recall@10 與 nDCG@10；近似找回率另對照同權限精確搜尋。量冷暖查詢 P95／P99、索引容量及更新耗時；不得用數學距離等價宣稱近似結果等價。

### R08：重排、補回上下文與有證據回答

- AI：排序模型評估問題與原文的關聯；回答模型引用原文證據，不引用生成問題當事實。
- 程式：先核權再送排序模型；限制候選數與輸入預算，補回父章節／鄰段／表頭並再次核權。回答送出前再驗版本、撤權與有效時間。
- 交付／驗收：跨段指代、例外、表格單位、錯引用、過期來源與缺證據時拒答；真人抽查「引用存在但不支持結論」。只增加重排或上下文其中一項做對照，再驗組合；報品質與延遲代價。

### R09：Agentic RAG 主動查證

- AI：判斷是否需要搜尋，拆問題、選來源、改問法、補讀及交叉查證；保留原問題的型號、否定、時間與範圍。
- 程式：沿用同一 Harness 和工具政策，限制查詢數、輪數、時間及費用；初始總共最多 3 次檢索、最多 2 輪重規劃，仍受總預算較嚴者約束。無證據或來源衝突不得硬答，取消停止後續查詢。
- 交付／驗收：留下每次查詢、取回證據、停止原因與結論對應；測必須跨文件才能答、無答案、衝突、假完成、工具失敗與文件注入。模型規劃紀錄不等於工具確實執行，須讀真回執。

### R10：建立可維護的知識與解答

- AI：從原文提議知識條目及可重用答案；程式保存候選、來源版本、支持段落、適用範圍、最後查證、到期時間及權限。
- 發布：具名真人確認，或由明確規則／原始數據獨立核對，才能依該類規則發布有效知識；AI 自評只留候選。跨來源答案使用可見權限交集。
- 交付／驗收：候選、有效、待查證、衝突與撤回狀態可讀回；來源變更時依賴答案、摘要、虛擬問題及快取都失效。測循環引用、矛盾說法及沒有原文支持的答案，不能越整理越偏離證據。

### R11：高頻維護與漏事件補查

- 程式：異動去抖、持久佇列、可重送去重與定期補掃；熱門範圍先以 5 分鐘核對缺漏，其餘 24 小時一輪為容量待驗目標。小檔無排隊目標 60 秒內更新；大檔與 OCR 獨立報積壓，不套同期限。
- 正確性：撤權／刪除先停止返回舊內容，再重建或回收衍生資料；來源不可達不當成已刪除。失效通知丟失時查詢端仍核對版本；遠端快變問題使用前重新查證。
- AI：只對受影響知識重新整理，不能把重新生成時間當來源最新時間。
- 交付／驗收：可控時鐘測連續存檔、改名、事件遺失／重送、磁碟移除、停機、解析中改檔、失效後崩潰；報最後成功查證、落後時間及失效傳播耗時。過期答案必須阻擋或明列待查證。

### R12：背景資源、停止與服務恢復

- 程式：掃描、解析、向量與維護共用總預算；前景保留資源，重解析獨立佇列。初始兩核心、4 GiB 背景記憶體、向量批次 8、10 GiB 索引上限都是待測配置，不是已證明所有模型可跑。
- 交付：狀態分發現、解析、向量化、有效知識、排除、不支援、失敗與積壓，分別列檔案數／bytes；可暫停、續跑、停用及調整資源。
- 驗收：索引啟用後前景 P95 相對基準增加不超過 20% 的既有目標；服務就緒後 5 秒內接受任務；容量滿停止新增而不刪原檔。以大檔、限額、服務重啟、取消及索引重建實測，不用小測試推論整機速度。

### R13：安全、備份與管理

- 程式：索引來源唯讀掛載；主機使用者權限映射；容器不得以 root 繞過；解析器無外網／巨集／模型秘密；模型外送使用獨立政策。任務授權 SQLite 與來源權限 PostgreSQL 各有擁有者，失聯時拒絕提供片段。
- 交付／驗收：文件／附件／網頁要求刪檔或外送不構成授權；跨使用者、跨工作區、舊快取及衍生問句皆不得漏資料。備份還原後先核對當前權限與來源，不把已撤回內容復活；備份保留與清理遵循明確政策。

### R14：正式安裝與兩個入口整合

- 程式：安裝器準備固定版本容器、資料表、獲准模型與來源設定；CLI 和桌面讀同一狀態與引用，不各建一套庫。無網路部署、缺件、錯版本、升級失敗及回退均有可理解的診斷。
- 真人：在乾淨受測電腦安裝，指定資料，立即工作；問一題、開原文、改檔、確認答案更新，再暫停／恢復、重開、備份／還原。領域使用者核對專業文件，IT 驗證部署與恢復。
- 放行：上述全流程及正式發布門檻通過，才算 RAG 產品能力交付；容器啟動或向量查詢成功不算完成。

### R15：品質方法與正式範圍收斂

逐一完成結構切片、語意切片、AI 選切點、虛擬問題多向量、片段背景、關鍵字混合、重排、父段補回與查詢改寫的有／無對照，保存未採用原因。不是所有方法都強制常開，而是每個已承諾候選都必須有研究、實測與取捨。最終固定預設及受支援選項，再用未調參題庫、真實代表資料、不同大小與格式驗收。

AI 審查先看方法及反例，再看同版輸出；真人核對語意品質、使用價值與專業內容；程式裁定權限、版本、執行及資源結果。任何安全越界不能用較高平均準確率抵銷。企業正式發布需要容量與長時間穩定性證據，60 題和單次掃描只作起點。

## 如何讓 AI 和真人真的能驗收

程式流程採「可重播資料＋固定預期＋真實結果讀回」。每個重要成功案例搭一個故意錯的案例，證明驗證器會拒絕；例如內容沒改卻回傳成功、取消後延遲寫入、引用已撤權文件。只測成功路徑不足以放行。

內容品質採「固定題庫＋隱藏標準答案＋盲評」。評分至少分相關性、原文支撐、完整性及是否適當拒答，不合成一個模糊總分。AI 評語必須指出原文位置；真人先標註基準題與爭議題，報 AI／真人分歧，不能只用模型互評。知識檢索的 60 題沿用既有驗收要求，另報各格式與題型分項；新方法先在開發題比較，再在未用來調參的題目驗證。樣本不足時只報觀察結果，不宣稱普遍有效。

真人操作單每案包含：版本／環境、準備資料、明確操作步驟、預期可見結果、失敗後如何接手、實際結果、證據位置、接受或退回及理由。五個試用任務至少涵蓋成功交付、拒絕、取消、重啟接續、知識更新；涉及畫面操作的任務在 P07 另驗。真人操作和模型模擬操作分開標記。

效能先固定硬體、文件數／容量、冷暖狀態及併發數，量首次可用時間、索引吞吐、記憶體／CPU 上限、查詢及取消延遲的中位數與 P95。原計畫既有目標不降低；尚未定值的項目在該步實作前固定可接受門檻，不能看完結果才調成通過。本文件沒有新的實測數據，不承諾掃完整台電腦需要幾小時。
