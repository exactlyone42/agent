# PLE 跑題記錄

這份文件記錄每次用 ple-harness 跑 PLEBench 題目的結果：用哪個模型、跑了多久、幾分、哪些檢查沒過、怎麼失敗的。原始檔留在 `.runtime/ple-env/c3/<run 名>/`，該資料夾被 .gitignore 排除，不進 Git，所以這裡是唯一進版控的摘要。

## 怎麼更新

- 每跑完一次，在「各次記錄」加一列；有失敗或沒過的檢查，補在「沒過的檢查與失敗原因」。每一條沒過的檢查都要寫原因：評分程式的 `why` 怎麼說、模型哪裡做錯；查不出原因就寫「未查證」，不留空。
- 分數看 `attempt1/jobs/dev/<題>__<碼>/verifier/reward.json`；17 條檢查的明細看同資料夾的 `eval.stdout.txt`。
- 與模型往來的記錄：本機有 `agent/trajectory.json`（每一步的訊息、工具呼叫、結果）與 `agent/serve.log`（呼叫失敗與重試）。Gateway 端的原始請求與回應不在本機，要請 ai-gateway 的 session 依下表的時間區間查。

## 改善方向（2026-11-21，來源：codex 獨立分析 `.runtime/codex-low-score.md` 加上本人核對 `serve.log`）

依效益排序。codex 只讀檔，沒重跑也沒重評；其中「新 harness 的漏洞」是讀程式碼的推論，不是實跑結果。

1. 強制早交完整初稿：heat 36 次缺檔重開說明「做完卻沒交檔」比上下文用完更常見。新 harness 目前只在上下文滿時拆項，缺檔仍原樣重開。做法：連續兩次缺檔就改計畫；先交一份能評分的 `submission.zip`，後面的項目只修改它。驗證：同題同預算，比較第一份 ZIP 出現時間；強制中斷時 ZIP 仍可被評分。
2. 先驗必要條件與跨檔數字：seismic 牆段數 3／2 對 5／6、mv 電纜容量 389 A 對 640 A，都是工程內容錯，與切分無關。做法：交件前讓一個新對話只對照任務文字的必要條件與數字。驗證：故意改錯牆段數、容量、登記表，確認檢查會擋下。
3. 提早存交接並保留父項要求：目前筆記在該項完成前才寫，上下文滿時可能還沒有；拆項時要確認子項涵蓋父項的全部交付要求。做法：每隔數次工具呼叫就更新筆記；拆項後比對父項輸出清單。驗證：同預算比較三題的交件時間、重開次數與分數。
4. 未查證：seismic G4／D1／D2／D3／D8 與 mv S01 為何算錯，需要讀軌跡才知道；新 harness 跑完後一併檢查。
