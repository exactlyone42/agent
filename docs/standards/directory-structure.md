# 目錄結構與檔案歸屬

這份是 repo（程式庫）目錄的唯一正式地圖。新增檔案前先查這裡，找得到歸屬就直接放；找不到再看文末的核准規則。`cargo xtask gate`（快速檢查命令）的第一步會拿 Git 追蹤的檔案比對本表，違反就失敗。

## 頂層

| 項目            | 放什麼                                                                                                                       | 不可放                                        |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `crates/`       | 所有 Rust 套件，一個子資料夾一個 crate                                                                                       | 散檔、非 crate 的資料夾                       |
| `sql/`          | 資料庫結構檔（`.sql`），一個版本一檔，由 Rust 用 `include_str!`（編譯時嵌入檔案內容）讀入                                    | Rust 程式、資料檔                             |
| `docs/`         | 繁中白話文件與圖形成品（PDF），只放在下面四個分類資料夾；一模組一份                                                          | 程式、產生的暫存檔、直接放在 `docs/` 根的檔案 |
| `loops/`        | 全案 LOOP（長任務計畫檔）與各票據（步驟任務卡）、檢查點（進度紀錄）                                                          | 第二份 LOOP、說明文件                         |
| `scripts/`      | 開發維運用的小工具與政策設定（含 `runtime_sweep.py` 清 `.runtime/`）                                                         | 產品邏輯                                      |
| `.repo-policy/` | 共用 Git 政策與 hooks（提交或推送時自動執行的檢查）安裝                                                                      | 專案程式                                      |
| `.cargo/`       | cargo（Rust 的建置工具）別名與變異測試（故意改壞程式驗測試）設定                                                             | 其他設定                                      |
| 根目錄檔案      | `README.md`、`PLAN.md`、`DEVELOPMENT.md`、`AGENTS.md`、`CLAUDE.md`，以及 Cargo、npm、toolchain（編譯工具版本）的設定與鎖定檔 | 實作檔、筆記、暫存檔                          |

## 名字看不懂的資料夾

這幾個都是工具自己會讀的，平常不用打開；表裡的「進 Git」指會不會被版本控制記錄。

| 資料夾          | 白話用途                                                                                                                                                                                     | 進 Git | 要自己動它嗎                                                                |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ | --------------------------------------------------------------------------- |
| `.cargo/`       | cargo（Rust 的建置工具）自動讀的設定。`config.toml` 限制同時編譯 2 個工作，並定義 `cargo xtask` 這個短指令；`mutants.toml` 列出變異測試要略過的、改了寫法但行為沒變的案例                    | 進     | 平常不用；改 `mutants.toml` 要同步 `docs/standards/mutation-equivalents.md` |
| `.repo-policy/` | 提交與推送時自動跑的檢查。`config.json` 規定哪些檔案要跑哪些命令（例如格式檢查），`install.py` 把它裝成 Git hooks（提交或推送時自動執行的程式），`policy.py` 執行檢查，`test_policy.py` 測它 | 進     | 不手改；要重裝時跑 `install.py`                                             |
| `.runtime/`     | 在這台電腦上跑命令留下的完整輸出與日誌，失敗時的錯誤訊息也存這裡；`checks/` 放 `cargo xtask all` 每一輪的原始證據                                                                            | 不進   | 每天自動清（規則見下方「`.runtime/` 自動清理」），不要放要保留的文件        |
| `target/`       | cargo 編譯出來的成品與快取                                                                                                                                                                   | 不進   | 不用管，可整個刪掉重編                                                      |
| `node_modules/` | `package.json` 裝的文件格式檢查工具（prettier）                                                                                                                                              | 不進   | 不用管，可整個刪掉重裝                                                      |

不進 Git 的資料夾由 `.gitignore` 排除，不受下面的自動檢查約束，也不需要登記在頂層表。

## `.runtime/` 自動清理

`scripts/runtime_sweep.py` 每天 03:30 由使用者層級的 systemd 排程（`runtime-sweep.timer`）執行，清掉 `.runtime/` 裡已經對不上現況的東西。預設只列出會刪什麼，加 `--apply` 才真的刪；每次結果追加到 `~/.local/state/runtime-sweep/log.jsonl`。

`.runtime/` 底下每個項目（一個檔案或一個資料夾）依序判斷，第一條成立就定案：

| 順序 | 條件                                                                      | 結果                         |
| ---- | ------------------------------------------------------------------------- | ---------------------------- |
| 1    | 有程序正開著裡面的檔案，或工作目錄在裡面                                  | 保留                         |
| 2    | 名字列在 `.runtime/.keep`（一行一個名字，`#` 開頭是備註）                 | 保留                         |
| 3    | 是 `checks/` 裡最新的 3 輪證據                                            | 保留                         |
| 4    | 裡面最後一次修改距今不到 1 天                                             | 保留（可能正在用）           |
| 5    | 名字含 commit 編號，且該 commit 已進 `origin/develop`、`main` 或 `master` | 刪（那一版已合併，不必再比） |
| 6    | 名字含 `YYYYMMDD` 日期，且該日期距今 7 天以上                             | 刪（標明是那天的產物）       |
| 7    | 裡面最後一次修改距今 7 天以上                                             | 刪（沒人再用）               |
| 8    | 其他                                                                      | 保留                         |

安全限制：`.runtime/` 必須是真資料夾（不是符號連結）且被 `.gitignore` 排除，否則整個略過；每次最多刪 200 項；只動 `.runtime/` 底下的項目，不碰別處。為什麼用修改時間而不是建立時間：重複寫入的日誌建立得早但仍在用，修改時間才反映有沒有人在碰它。放棄的做法：只靠修改時間一條規則，因為「合併後已作廢的比對基準」不一定超過 7 天，會讓這類資料多放一週。

要把某個東西留久一點，把名字加進 `.runtime/.keep`；要手動跑一次：`python3 scripts/runtime_sweep.py --repo .`（預覽）、`--apply`（實刪）。

## 什麼工作存哪裡

| 我要做的事                               | 放這裡                                                            | 補充                                                                                                                                                                                                                         |
| ---------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 新增或修改產品功能                       | 負責該功能的 crate 的 `src/`（見下表「crates 內部」）             | 先找已有職責的 crate，不另開                                                                                                                                                                                                 |
| 為功能寫測試                             | 同一個 crate 的 `tests/`                                          | 測試輔助放 `tests/support/`                                                                                                                                                                                                  |
| 新增命令列指令                           | `crates/cli/src/command/`，一個指令一個檔，並在 `command.rs` 登記 | 指令名稱、環境變數名等固定字串放 `settings.rs`                                                                                                                                                                               |
| 改資料庫結構                             | `sql/` 新增下一個版本檔 `store_v<N>.sql`                          | 舊版本檔不可改（已建好的資料庫靠它升級）                                                                                                                                                                                     |
| 同一個 crate 內多個檔案共用的內部項目    | 該 crate 的 `src/prelude.rs`，用 `pub(crate) use` 收齊            | 只放 2 個以上檔案用到的項目；每個檔案以 `use crate::prelude::*;` 引入。模組宣告放 crate 根檔（`<crate 名>.rs`），不用 `mod.rs`；同類檔案放進以功能命名的子資料夾（如 `store/`），子資料夾的模組宣告放同名檔（如 `store.rs`） |
| 寫設計說明、取捨、使用方式               | `docs/design/`，一個模組一份，並在 `README.md` 索引表加一列       | 不另開資料夾                                                                                                                                                                                                                 |
| 畫架構圖或流程圖                         | `docs/diagrams/`，輸出成 PDF                                      | 每頁要有不透明白底                                                                                                                                                                                                           |
| 記錄每一輪做了什麼、學到什麼             | `docs/standards/records.md`                                       | 格式見該文件                                                                                                                                                                                                                 |
| 長任務的計畫、每一步的任務卡、進度       | `loops/`                                                          | 進度只能用 checkpoint 工具寫，不手改                                                                                                                                                                                         |
| 開發用的小工具或腳本（Python、Shell 等） | `scripts/`                                                        | 腳本不可放別處                                                                                                                                                                                                               |
| 定期排程（systemd 計時器）與安裝腳本     | `scripts/schedule/`                                               | 用法與退回見 `docs/standards/drift-review.md`                                                                                                                                                                                |
| 提交與推送時要自動跑的檢查               | `.repo-policy/config.json`                                        | 只在這裡改檢查項目                                                                                                                                                                                                           |
| 品質檢查（格式、clippy、測試、變異測試） | `crates/xtask/`，用 `cargo xtask gate` 與 `cargo xtask all` 跑    | 結構檢查的登記表在 `crates/xtask/src/scan/structure_violations.rs`                                                                                                                                                           |
| 命令輸出、除錯日誌、一次性試跑結果       | `.runtime/`                                                       | 不進 Git；別放在根目錄                                                                                                                                                                                                       |
| 新增 crate、頂層項目、crate 內新種類項目 | 先取得使用者同意                                                  | 同一次提交更新本文件與登記表                                                                                                                                                                                                 |

找不到對應的列時，不要自己找地方放；先問，或看文末的核准規則。

## crates 內部

每個 crate 只放三樣：`Cargo.toml`（套件設定檔）、`src/`、`tests/`。需要 `build.rs`（編譯前先跑的程式）、`examples/`、`benches/`（效能測試）這類新項目，屬於結構變更，要先核准。

| crate          | 責任                                                           | 不可含               |
| -------------- | -------------------------------------------------------------- | -------------------- |
| `harness`      | 自寫的 agent 迴圈與事件契約（約定事件的格式與意義）            | 特定模型或服務的接線 |
| `capabilities` | 迴圈、工具呼叫等能力：只收事件、提出意圖                       | 排程、特定模型接線   |
| `openai`       | 對 OpenAI 相容 Gateway（模型閘道）的接線                       | 批准、任務庫         |
| `approval`     | 敏感工具的批准閘門                                             | 模型呼叫             |
| `agent`        | 任務、任務庫、輸入檢查、驗證結果，以及把批准閘門接到任務的程式 | 命令列解析           |
| `cli`          | 命令列入口與輸出                                               | 核心邏輯             |
| `xtask`        | 快檢（`cargo xtask gate`）與完整檢查（`cargo xtask all`）      | 產品功能             |

已核准、尚未建立（`capabilities` 已於 M2 建立，在上表）（使用者 2026-11-16 同意；依「不建立未使用 crate」，在要放程式的步驟才建，同一個提交更新上表與登記表）。M2、M4 是實作步驟編號，見 [mortal agent](../design/mortal-agent.md)：

| crate       | 責任                           | 不可含         | 建立步驟 |
| ----------- | ------------------------------ | -------------- | -------- |
| `scheduler` | 排程算法、收件匣、單一活動執行 | 迴圈、工具呼叫 | M4       |

## docs/ 的分類

`docs/` 根目錄不放檔案，每份文件必須在下面四個資料夾之一；新增分類要先取得使用者同意（使用者 2026-11-18 要求文件要分類）。

| 資料夾       | 放什麼                                                           | 目前的檔案                                                                                                        |
| ------------ | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `design/`    | 設計、取捨與使用方式：每個部件做什麼、為什麼這樣做               | `architecture.md`、`mortal-agent.md`、`agent-method.md`、`knowledge-plan.md`、`cli.md`                            |
| `standards/` | 規範與紀錄：品質要求、目錄地圖、記事格式、變異測試例外與既有債務 | `engineering-standards.md`、`directory-structure.md`、`records.md`、`mutation-equivalents.md`、`mutation-debt.md` |
| `research/`  | 研究與評測：來源查證、驗收案例                                   | `sources.md`、`evaluation.md`                                                                                     |
| `diagrams/`  | 圖形成品與圖文版 PDF：現況圖、目標圖、計畫的圖文版               | 現況與目標的架構圖與類別圖、`PLAN.pdf`                                                                            |

## 檔案與命名

- 獨立函數一檔一個；型別連同它的方法同檔（見 AGENTS.md）。
- 不建 `misc`、`common`、`helper(s)`、`util(s)`、`shared`、`temp`、`tmp` 目錄，任何層級都不行（檔名可以含這些字，資料夾名不行）。需要共用時，先找真正擁有該職責的 crate。
- 測試放各 crate 的 `tests/`；測試輔助放 `tests/support/`。

## 自動檢查的規則

下面每一條都由 `cargo xtask gate` 的第一步檢查，`cargo xtask all` 也會跑；push 或發版前一定會被檢查一次。每條規則在 `crates/xtask/tests/structure.rs` 都有通過與故意違反兩種測試樣本。

| 規則                                                                                   | 為什麼                                                              |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 空檔案不可進 Git                                                                       | 空檔案沒有內容，多半是殘留                                          |
| `.log`、`.pid`、`.tmp`、`.out`、`.err`、`.lock` 不可進 Git（`Cargo.lock` 除外）        | 這些是執行時產生的，不是原始檔；`Cargo.lock` 記錄套件版本，要進 Git |
| `.py`、`.sh`、`.ps1`、`.bat` 只能放 `scripts/` 與 `.repo-policy/`                      | 要執行的腳本（Python、Shell 等）集中一處，才找得到                  |
| `.sql` 只能放 `sql/`                                                                   | 資料庫結構不混在 Rust 程式旁                                        |
| `docs/` 只放 `.md` 與 `.pdf`                                                           | 文件資料夾不放程式與原始圖檔                                        |
| `docs/` 的檔案必須在 `design`、`standards`、`research`、`diagrams` 之一                | 文件不能什麼都往 `docs/` 根目錄丟，要依用途分類                     |
| `docs/` 的每個檔案，至少要被另一份文件或程式用檔名提到                                 | 沒人提到的文件，讀者根本找不到                                      |
| 兩份文件不能有逐字相同、30 字以上的同一行（表格、標題、以 `- [` 開頭的連結清單行除外） | 同一件事只記一處，改的時候不漏                                      |
| `crates/*/src/` 的 `.rs` 檔不可有中日韓文字（檔名以 `_text.rs` 結尾的訊息表除外）      | 給使用者看的字只放在各語言的訊息表，換語系時不必翻遍整份程式        |

最後一條只抓得到逐字複製；換句話說的重複，仍要審查時用人眼看。

## 結構變更的核准

| 動作                                                    | 誰決定                    |
| ------------------------------------------------------- | ------------------------- |
| 在既有 crate 的 `src/` 或 `tests/` 內新增檔案或子資料夾 | AI 自行決定，要有明確職責 |
| 新增 crate、頂層項目、crate 內新項目，或調整上表        | 先取得使用者同意          |
| 大量搬移、刪除或合併既有模組                            | 先取得使用者同意          |

核准後，同一個提交要一起改這份文件與 `crates/xtask/src/scan/structure_violations.rs` 的登記表，兩邊不一致就是錯。

## 完成前自查

- 新增的檔案與資料夾是否都在上表有歸屬。
- 是否已有同職責的檔案或 crate，被重複建立。
- `git status` 與 `git diff --stat` 有沒有意外產生的檔案。
